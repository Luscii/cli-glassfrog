# Deprecations

Retired decisions, patterns, and features. Each entry records what was superseded, what replaced it, and where it originated. Managed by the deprecate skill via memory-protocol.md.

- [decision] [ASSUMED] Request Authentication ↔ Connection Configuration composition seam — how 007 obtains the credential (re-resolve from Discovery vs. read from the connection context) → connection context is the single resolution point; 010 replays it into 007's AuthTransport (from 007-request-authentication, 2026-06-06)
  Superseded by 009-connection-context-assembly ADR-2: ConnectionContext carries the resolved credential, and Request Execution (010) wires AuthTransport with a resolver that replays the context's cached credential rather than re-resolving from Discovery — so 007 reads the token from the context. Resolves the seam 007 flagged and 008 carried open. (The package-name half of 007's [ASSUMED] seam was already fixed by 008: internal/apiclient.)

- [decision] Undecodable 2xx body → `RuntimeError` (exit 1, internal error) → `APIError` (exit 3, general API error) (from 011-identity-read, 2026-06-10)
  Superseded by 031-diagnostic-normalization ADR-2 (developer-confirmed clarification): a `*apiclient.DecodeError` — a 2xx response whose body would not decode — is an API-exchange problem (the API answered in an unreadable shape), not a CLI-internal fault, so it now classifies `APIError`/3. The cause/next-step wording ("the API response did not match the expected shape — … report it") is unchanged. Render-template failures (019, `*RenderError`) stay `RuntimeError`/1, so the split sharpens "the API's fault" (3) vs. "our fault" (1) rather than blurring it. Originated as the `classifyClientError` decode arm in 011 and was echoed by 012/013/014's "undecodable 2xx → RuntimeError(1)" scenarios and by the decode→1 rows in 011/012/014/025/026/034 interface-cli.md and docs/reference/*.md — those prose references remain at the old wording and should be reconciled when those features are next touched or their docs regenerated (see LEARNINGS 2026-06-10).

  Superseded by 030-release-drafting ADR-4: Release Drafting needs a label-driven way to exclude spec/feature-only and maintainer-flagged PRs from the notes and the bump (release-drafter filters by label only, with no path-based exclusion), so an eighth managed label `no-release-note` will be added to `.github/settings.yml` and `.github/labeler.yml` (applied via a `negate`-over-noteworthy matcher) by 030 task T001. The decision is recorded now; the implementation is deferred to T001, so until then the repo's managed set is still seven. The seven release-note *categories* are unchanged regardless — the eighth label is an exclusion marker, not a category, and `breaking`/`features`/`fixes` still double as the semver signal. 030's `internal/build` config guard (ADR-6) will re-pin the eight-label invariant, closing 028's "un-guarded until 030 ships" note. PROSE TO RECONCILE: 028's plan.md and interface-spec.md are reconciled by the 030 PR (forward-pointers to this entry). What remains until T001 lands: the `.github/labeler.yml` + `.github/settings.yml` header comments still read "seven managed labels" — correct for now, updated by T001. (028's spec.md describes seven *categories*, which stay accurate.)
- [decision] 039's forecast that 040 would REMOVE the three divergent per-domain `Source` enums (collapse `auth.Source` / `apiclient.BaseURLSource` / output's selection vocabulary onto the one `resolve.Provenance` shape) → surface-stable retrofit: keep every per-domain type/enum, map `resolve.Provenance` back internally; the enum-unification end-state is DEFERRED to a possible later cleanup spec (from 039-source-composed-resolution, 2026-06-12)
  Retires the tail of 039's "value validation moves to the call site" DECISIONS entry ("the three divergent per-domain `Source` enums collapse onto the one `Provenance` shape — their removal is 040's work, not 039's"). Superseded by 040-resolution-call-site-retrofit ADR-1 (developer-confirmed during 040 planning): each resolver became a thin adapter that composes `resolve.Resolve(...)`, takes the winner, and maps `resolve.Provenance.Kind` → its existing enum member (+`Origin`→`Path`/error label), so `auth.Resolution`/`auth.Source`, `apiclient.BaseURL`/`BaseURLSource`/`*BaseURLError`, and `output.Selection`/`*FormatError` keep their fields, members, and message shapes exactly; `resolve.Provenance` is an internal intermediate never exposed past the three resolver functions. WHY the forecast was retired rather than honoured: 039 recorded no DECISIONS entry, so its "remove the enums" line was an unratified forecast; DECISIONS §74 ratifies "`internal/auth` keeps `Resolution`/`Source`"; and removing the enums would ripple into `Identity` (transport.go) and `ConnectionContext.Complete()`/`Ready()`/status rendering (context.go) — exactly the readiness logic 039's own risk register flagged as high-impact drift. 039's "one uniform provenance vocabulary" end-state is not reached by 040; it remains available as a later cleanup spec if the consumer-facing simplification is ever judged worth that blast radius.

- [decision] 022's `release: { mode: keep-existing }` defensive default (never replace an existing release's body/status on a direct `goreleaser release`) (from 022-automated-release-pipeline, 2026-06-08)
  Superseded by 036-homebrew-tap (interface "Refinements to 022's sections" + config-guard): `release.disable: true`. The Homebrew tap job runs `goreleaser release` to push the formula, and that invocation must not create or modify the GitHub release at all — disabling the release publisher is the strict form of `keep-existing` (never touch it, vs. keep an existing body). Asset attachment + status stay with the publish job's `gh release upload` and #30. The `internal/build` config-guard now pins `release.disable: true` (it previously pinned `mode: keep-existing`).

- [decision] The release pipeline runs "entirely within the repo (only `GITHUB_TOKEN`)" (DECISIONS 179 / 022) (from 022-automated-release-pipeline, 2026-06-08)
  Superseded by 036-homebrew-tap ADR-4: publishing the formula to the separate tap repo (`Luscii/homebrew-cli-glassfrog`) needs cross-repo `contents: write`, which `GITHUB_TOKEN` cannot grant. The `tap` job injects a cross-repo token as `HOMEBREW_TAP_TOKEN` (sourced from the org `CI_GITHUB_TOKEN` secret), referenced only in that job. The build/verify/publish spine is still `GITHUB_TOKEN`-only; the new credential touches only the tap push.

- [decision] ADR-1 "distribute as a GoReleaser Homebrew **formula** (`brews`), not a cask" — re-affirmed against GoReleaser's deprecation of `brews` (from 036-homebrew-tap, 2026-06-13)
  Not retired — re-affirmed with a guardrail. GoReleaser deprecated the `brews` (formula) publisher in favour of `homebrew_casks` (soft since v2.10). Migrating would break ADR-1's reason for choosing a formula: casks are macOS-only, and the spec needs Linux too. Decision (developer-confirmed): keep `brews` and **pin** `release.yml`'s GoReleaser to the `~> v2.16` line so a future v2 that removes `brews` can't silently break the tap job; revisit only if Homebrew/GoReleaser offer a cross-platform pre-built-binary path. Tracked in `.goreleaser.yaml`/`release.yml` comments and LEARNINGS (2026-06-13).

- [pattern] The LEARNINGS 2026-08-05 provisional entry as the home for the circle-routing fact F7 (`proposal create` has no circle parameter; the proposal lands in the circle of the anchor tension's sensing role; own-circle changes route to the parent, with the Circle Lead exception) → the canonical record at `plugin/skills/proposal-drafting/references/circle-routing-rule.md` (from 073-circle-routing-rule, 2026-08-08)
  Superseded by 073-circle-routing-rule (plan ADR-5). The routing rule recorded provisionally as LEARNINGS 2026-08-05 F7 now lives in the circle-routing record — the rule, the classification test, and the procedure with its named reads. The record is the single source; the LEARNINGS entry keeps its forward pointer (it already names this capability) and git history is the changelog — no second copy of the routing content is introduced here or anywhere. Go-forward retirement is **whole-record** and its trigger is **premise dissolution**: if `proposal create` ever gains a circle parameter, the anchor no longer determines the circle, so the rule is not merely stale but wrong — delete the record and add a `/score:deprecate` entry naming the spec revision that dissolved the premise, in one change. A change to a *consequence* (say, the Circle Lead exception alone) is an ordinary edit, not a retirement. Contrast with the sibling grammar record's three-part retirement above: this record carries **no live-facts manifest to keep in step**, so retirement cannot collide with its guard — there is no per-fact granularity, and applying the sibling's per-fact flow here would be the wrong flow.

- [pattern] The LEARNINGS 2026-08-05 provisional entry as the home for the change-set grammar facts F5/F6 (own-circle `CreatePolicy` shape; self-targeting `UpdateRole` accepted-but-invalid) → the canonical record at `plugin/skills/proposal-drafting/references/change-set-grammar-facts.md` (F5 → CSG-1, F6 → CSG-2) (from 072-change-set-grammar-facts, 2026-08-08)
  Superseded by 072-change-set-grammar-facts (plan ADR-4). The two write-path shapes recorded provisionally as LEARNINGS 2026-08-05 F5 and F6 now live in the record as facts **CSG-1** (F5: own-circle policy is a top-level `CreatePolicy` part with no `UpdateRole` wrapper) and **CSG-2** (F6: an `UpdateRole` self-targeting the circle is accepted at create but returned `valid: false`). The record is the single source; the LEARNINGS entry keeps its forward pointer and git history is the changelog — no second copy of the fact content is introduced here or anywhere. The LEARNINGS entry's other facts (F1–F4, F7–F10) are untouched: only F5/F6 moved. Go-forward retirement, when the published contract later absorbs a shape, is a **deliberate three-part act in one change**: (1) delete the fact's `## CSG-<n>` section from the record; (2) drop its id from the record's `Live facts` manifest — omit this and the sibling `internal/build` guard fails, which is the design; (3) add a `/score:deprecate` entry naming the spec revision that absorbed the shape. When the **last** fact retires, the record file itself is deleted, not kept as an empty shell (the guard's non-empty invariant enforces this). Retired fact ids (`CSG-1`, `CSG-2`, and any successor) are **allocated monotonically and never reused** — a retired id stays the permanent handle for that shape, so this and any downstream reference remains unambiguous.

- [decision] 074 ADR-2's clause that `proposal create` reports `Success` for **all four** verdict states — i.e. a created-but-invalid proposal still exits `0` → `InvalidCreate` (exit code `8`) for the `valid: false` state; the three remaining verdict states keep `Success`/`0` (from 074-post-create-validity-read, 2026-08-08)
  Superseded by 078-invalid-create-outcome ADR-1/ADR-4. Only the **four-states clause** retires; ADR-2's load-bearing half — that the *secondary* read-back's own failure is never the command's failure and never withholds the primary write's returned `prp_` id — **stands unchanged**, and 078 upholds it (an unobtainable or unstated verdict still exits `0`, and the failure it does introduce carries the `prp_` id in the envelope). 074 named this retirement in advance: its own entry recorded the exit-`0` consequence as "deliberately accepted and NOT hidden … the new Outcome + exit code is the dependent Invalid-Create Outcome's content", and its checklist raised it as P2-1. The reason it could not simply be folded into 074: a new outcome touches the `Outcome` switch sites and the published exit-code convention, which is a reviewable change of its own. ALSO NARROWED, NOT RETIRED, by the same change: 074 ADR-5's rule that the create's machine path emits the read-back document verbatim with a `verdict_source` advisory on stderr now governs the **success** outcomes only — on the `valid: false` failure, stdout carries the 032 failure envelope and no advisory (078 ADR-4). The verbatim-server-document invariant (018) is untouched: no document is reshaped, one is withheld from stdout on a failure, exactly as every other failure already does. Retirement trigger for the successor, should it ever come: if the server stops carrying `valid` on the single-proposal read, the trigger can never fire and 078's outcome becomes unreachable rather than wrong — that is a premise dissolution, and the whole outcome retires with a fresh entry naming the contract revision.

Notes on executing this removal (verified against the runners and the Go tests during 078's pre-implementation guard):

0. **The collision has a Go half too.** Six unit tests in `internal/cli/proposal_readback_test.go` assert `Success` against the shared not-valid fixture; no tag filter reaches them, so they are re-pointed or inverted in the same change (078 tasks.md T003).
1. **Three of the four `@deprecate` scenarios actually execute** — lines 35, 124, and 146 carry no `@wip`, and each asserts `exit with code 0` against a *not valid* read-back, so they fail the moment 078's behaviour lands. The fourth (line 205) is `@validation @wip`, already excluded; its retag is bookkeeping only.
2. **Retagging alone is inert.** `@deprecate`/`@deprecated` are read by nothing in this repo — every runner filters `~@wip` only. The governance removal must therefore also add `~@deprecated` to the `Tags` filter in `internal/cli/post_create_validity_read_bdd_test.go` (the only runner loading that file, by exact path), which is what finally gives the tag the exclusion its documented lifecycle promises.
3. **"→ active" does not apply uniformly to the six replacements.** All six drop `@pending-deprecation`; the five behaviour scenarios also drop `@wip` and become active, while the `@validation` one keeps `@validation @wip` because it is held out for independent verification.
4. **Pairing is not 1:1 — four deprecations, six replacements, because two of the four are answered twice.** The deprecated *structured-output* scenario is answered by both "A machine-readable failure carries the structured envelope" (the failure path) and "Structured output carries the verdict for a valid create" (the success re-pin). Likewise the deprecated compact scenario is answered by two replacements — the valid-fixture re-pin ("The compact line carries the validity token for a valid create") and the new failure-path scenario ("The compact format fails the create the same way"), which together preserve the compact coverage across both outcomes.

All of the above happens in the **same change** that implements the new outcome (078 tasks.md T003), never after it.
