# Deprecations

Retired decisions, patterns, and features. Each entry records what was superseded, what replaced it, and where it originated. Managed by the deprecate skill via memory-protocol.md.

---

- [decision] [ASSUMED] Request Authentication ↔ Connection Configuration composition seam — how 007 obtains the credential (re-resolve from Discovery vs. read from the connection context) → connection context is the single resolution point; 010 replays it into 007's AuthTransport (from 007-request-authentication, 2026-06-06)
  Superseded by 009-connection-context-assembly ADR-2: ConnectionContext carries the resolved credential, and Request Execution (010) wires AuthTransport with a resolver that replays the context's cached credential rather than re-resolving from Discovery — so 007 reads the token from the context. Resolves the seam 007 flagged and 008 carried open. (The package-name half of 007's [ASSUMED] seam was already fixed by 008: internal/apiclient.)

- [decision] Undecodable 2xx body → `RuntimeError` (exit 1, internal error) → `APIError` (exit 3, general API error) (from 011-identity-read, 2026-06-10)
  Superseded by 031-diagnostic-normalization ADR-2 (developer-confirmed clarification): a `*apiclient.DecodeError` — a 2xx response whose body would not decode — is an API-exchange problem (the API answered in an unreadable shape), not a CLI-internal fault, so it now classifies `APIError`/3. The cause/next-step wording ("the API response did not match the expected shape — … report it") is unchanged. Render-template failures (019, `*RenderError`) stay `RuntimeError`/1, so the split sharpens "the API's fault" (3) vs. "our fault" (1) rather than blurring it. Originated as the `classifyClientError` decode arm in 011 and was echoed by 012/013/014's "undecodable 2xx → RuntimeError(1)" scenarios and by the decode→1 rows in 011/012/014/025/026/034 interface-cli.md and docs/reference/*.md — those prose references remain at the old wording and should be reconciled when those features are next touched or their docs regenerated (see LEARNINGS 2026-06-10).

- [decision] The managed PR-label family is EXACTLY the seven release-note categories / NO parallel namespace → 030's design introduces an eighth managed label (`no-release-note`, exclusion); the managed set becomes eight once 030 task T001 lands it (from 028-pr-administration, 2026-06-09)
  Superseded by 030-release-drafting ADR-4: Release Drafting needs a label-driven way to exclude spec/feature-only and maintainer-flagged PRs from the notes and the bump (release-drafter filters by label only, with no path-based exclusion), so an eighth managed label `no-release-note` will be added to `.github/settings.yml` and `.github/labeler.yml` (applied via a `negate`-over-noteworthy matcher) by 030 task T001. The decision is recorded now; the implementation is deferred to T001, so until then the repo's managed set is still seven. The seven release-note *categories* are unchanged regardless — the eighth label is an exclusion marker, not a category, and `breaking`/`features`/`fixes` still double as the semver signal. 030's `internal/build` config guard (ADR-6) will re-pin the eight-label invariant, closing 028's "un-guarded until 030 ships" note. PROSE TO RECONCILE: 028's plan.md and interface-spec.md are reconciled by the 030 PR (forward-pointers to this entry). What remains until T001 lands: the `.github/labeler.yml` + `.github/settings.yml` header comments still read "seven managed labels" — correct for now, updated by T001. (028's spec.md describes seven *categories*, which stay accurate.)
- [decision] 039's forecast that 040 would REMOVE the three divergent per-domain `Source` enums (collapse `auth.Source` / `apiclient.BaseURLSource` / output's selection vocabulary onto the one `resolve.Provenance` shape) → surface-stable retrofit: keep every per-domain type/enum, map `resolve.Provenance` back internally; the enum-unification end-state is DEFERRED to a possible later cleanup spec (from 039-source-composed-resolution, 2026-06-12)
  Retires the tail of 039's "value validation moves to the call site" DECISIONS entry ("the three divergent per-domain `Source` enums collapse onto the one `Provenance` shape — their removal is 040's work, not 039's"). Superseded by 040-resolution-call-site-retrofit ADR-1 (developer-confirmed during 040 planning): each resolver became a thin adapter that composes `resolve.Resolve(...)`, takes the winner, and maps `resolve.Provenance.Kind` → its existing enum member (+`Origin`→`Path`/error label), so `auth.Resolution`/`auth.Source`, `apiclient.BaseURL`/`BaseURLSource`/`*BaseURLError`, and `output.Selection`/`*FormatError` keep their fields, members, and message shapes exactly; `resolve.Provenance` is an internal intermediate never exposed past the three resolver functions. WHY the forecast was retired rather than honoured: 039 recorded no DECISIONS entry, so its "remove the enums" line was an unratified forecast; DECISIONS §74 ratifies "`internal/auth` keeps `Resolution`/`Source`"; and removing the enums would ripple into `Identity` (transport.go) and `ConnectionContext.Complete()`/`Ready()`/status rendering (context.go) — exactly the readiness logic 039's own risk register flagged as high-impact drift. 039's "one uniform provenance vocabulary" end-state is not reached by 040; it remains available as a later cleanup spec if the consumer-facing simplification is ever judged worth that blast radius.
