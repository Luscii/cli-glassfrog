### 2026-06-03 — cobra injects `completion` and `help` commands outside the registration guard
(Found during [T004](../../specs/001-command-registration/tasks.md) implementation)

- **Type**: design-issue
- **Location**: `internal/cli` (cobra root command), surfaces in `glassfrog --help` / command listing
- **Severity**: low — expected cobra behavior; no impact on Command Registration's guarantees, but it affects sibling capabilities.
- **Description**: cobra automatically adds built-in `completion` and `help` subcommands to the root. These are framework-provided and do **not** pass through our `Register`/`MustRegister` guard, so they are not subject to the fail-loud rules and they appear in the command listing alongside guard-registered commands.
- **Suggested action**: The **Help & Version** spec (and **Argument Dispatch**) should decide explicitly how to treat cobra's built-ins — list them, hide them, or replace cobra's default help — rather than assuming every visible command came through the guard. If the built-ins are unwanted, disable `completion` via `cmd.CompletionOptions.DisableDefaultCmd = true`. For `help`, note the subtlety surfaced in PR #5 review: `SetHelpCommand(&cobra.Command{Hidden:true})` only hides the command from listings — `glassfrog help` **still resolves**. cobra has no clean "no help command" switch: `InitDefaultHelpCmd` (called inside `ExecuteC`, after `Assemble`) always attaches *some* help command when the root `HasSubCommands()`, so a placeholder must occupy the slot. **The right placeholder carries an empty `Use` (`SetHelpCommand(&cobra.Command{Hidden: true})`) — not a non-`help` name.** 003 implemented `Use: "__help_disabled"` first, but PR #6 review caught that a *named* placeholder is itself a resolvable invented path: `glassfrog __help_disabled` resolved as a hidden child and returned `Success` with empty output, contrary to the no-invented-commands / no-fabricated-usage non-behaviors. An empty-`Use` placeholder has no typeable token — `glassfrog help` and `glassfrog __help_disabled` are both unknown commands, and even a degenerate empty argument is rejected as unknown rather than silently succeeding; the `--help` flag is unaffected. Resolved by 003 (ADR-2) as implemented in PR #6. **Test note**: assert the *invariants* — built-ins absent + alphabetical relative order (`roles` before `version`) — rather than pinning the full top-level set (`"roles,version"`), so adding a legitimate command later does not break the help test (PR #6 review).

### 2026-06-03 — cobra rejects unknown subcommands only at the root, not under nested groups
(Found during [T002](../../specs/002-argument-dispatch/tasks.md) implementation)

- **Type**: design-issue
- **Location**: `internal/cli/dispatch.go` (`Run`), surfaces for any `glassfrog <group> <typo>` invocation.
- **Severity**: medium — without handling, an unknown subcommand under a group fails open (prints the group's help, returns no error), violating the dispatch contract that every unmatched token is a `UsageError`.
- **Description**: cobra's default arg validator (`legacyArgs`) only emits an `unknown command` error when the command has **no parent** (the root). A non-runnable nested group (e.g. `roles`) given an unknown subcommand (`lst`) returns `flag.ErrHelp` *before* arg validation runs, so cobra prints the group's help and `Execute` returns `nil`. Setting `Args: cobra.NoArgs` on the group does **not** fix this — `Find` skips `legacyArgs` once `Args` is non-nil, and the `!Runnable() → flag.ErrHelp` early return still pre-empts `ValidateArgs`. Our registration guard also forbids giving a group a `RunE` (a command is leaf-with-action XOR group-with-children), so the group cannot be made runnable to intercept the args. Dispatch therefore detects the swallowed token itself: after `ExecuteC`, when the executed node is a non-runnable group and `executed.Flags().Args()` (cobra's own flag-stripped positional remainder) is non-empty, `Run` synthesizes `unknown command "<token>" for "<path>"` and classifies `UsageError`. **Because cobra returned `nil` here it printed no error of its own, so `Run` must also write the synthesized error (plus a `Run '<path> --help' for usage.` pointer) to `executed.ErrOrStderr()` — otherwise the operator sees only the group help and never which token was unrecognized (PR #4 review, round 1).** This stderr write belongs in `Run`, not the entrypoint: blanket-printing returned errors in `main.go` would double-print the errors cobra already emits itself (root unknown command, unknown flag).
- **Suggested action**: **Help & Version (003)** owns help-text rendering and the keep/hide of built-ins; if it customizes the help command or the not-runnable behavior, re-verify this swallow-detection still fires. **Exit-Code Convention (004)** maps the `UsageError` category — note that the nested-group unknown-subcommand path produces `UsageError` via a *synthesized* error (not a cobra-native one), so any error-type inspection in 004 must not assume a cobra sentinel.

### 2026-06-03 — cobra leaf commands accept arbitrary positional args unless they declare an `Args` validator
(Found during PR #4 review of [002-argument-dispatch](../../specs/002-argument-dispatch/tasks.md))

- **Type**: design-issue
- **Location**: leaf command constructors (`version.go`, `roles.go`); classification in `internal/cli/dispatch.go` (`Run`).
- **Severity**: medium — without an `Args` validator a leaf silently ignores extra positional tokens (`glassfrog version extra` runs the action and drops `extra`), violating the Invalid-input accord ("unexpected input is never silently ignored; the command does not run").
- **Description**: a cobra command with no `Args` field defaults to `ArbitraryArgs`, accepting any positional tokens and passing them to the action. Each leaf must declare what it accepts: leaves with no positional arguments set `Args: cobra.NoArgs`; a leaf taking a fixed argument (e.g. a future `roles get <role-id>`) sets `cobra.ExactArgs(n)`. The acceptance contract is per-command, so dispatch can't enforce it generically — but it must *classify* the rejection. cobra runs `ValidateArgs` before the action, so when `Run`'s runnable-command arm sees a non-nil `err`, it re-checks `executed.ValidateArgs(executed.Flags().Args())`: non-nil means the command refused an unexpected arg (`UsageError`, action never ran); nil means the action ran and the error is its own runtime failure (`Success`, with the error returned — `RuntimeError` deferred to 004).
- **Suggested action**: every new leaf must declare an `Args` validator matching its positional contract. Consider whether the **Command Registration** guard should *require* an explicit `Args` validator on leaves (fail-loud) so this can't be forgotten — today it is a convention, not an enforced rule. **Mirror the contract in every test fixture**: when production leaves gained `NoArgs`, the unit-test tree (`dispatchTree`'s `mark`) was updated but the BDD `recordingLeaf` was initially missed (PR #4 review, round 2). A test fixture that omits the validator silently diverges from production and can let a future scenario pass extra positional tokens that real commands would reject — so when you add a per-command constraint, audit *both* the unit-test tree and the BDD harness for parity.

### 2026-06-04 — `SilenceErrors` swallows pre-`RunE` arg errors: print them from dispatch, NOT the `Args` func (it is re-invoked)
(Found during PR #16 rounds 3–4 review of [006-credential-storage](../../specs/006-credential-storage/tasks.md); code in `internal/cli/authcmd.go`, `internal/cli/dispatch.go`)

- **Type**: design-issue
- **Location**: `internal/cli/dispatch.go` (`Run`, arg-rejection branch) and any leaf that sets `SilenceErrors`/`SilenceUsage` and relies on `RunE` to emit its own operator-facing messages.
- **Severity**: medium — round 3: a usage error (`auth login a b`) gave a bare exit code 2 with **no message** (silent crash); round 4: the round-3 fix then printed the message **twice**.
- **Description**: `auth login` sets `SilenceErrors`/`SilenceUsage` so `runLogin` controls every message (path-only, never the token). But cobra runs the `Args` validator (`MaximumNArgs(1)`) *before* `RunE` — a rejected positional returns straight out of `ExecuteC`, never reaching `RunE`, and `SilenceErrors` suppresses cobra's own dump. `dispatch.Run` classifies it as `UsageError` (→ code 2) but printed nothing. This is the trap hiding *behind* the line-27 learning ("declare an `Args` validator"): declaring it is necessary but not sufficient once you silence cobra. **Round 3 fixed it the wrong way** — by printing inside a custom `Args` func. That double-printed, because `dispatch.Run` *re-invokes* `executed.ValidateArgs(...)` to classify the rejection (tell an arg error apart from a runtime error), so a side-effecting validator runs its print twice. **Round 4** is the correct shape: keep `Args` side-effect-free (`cobra.MaximumNArgs(1)`), and emit the `Error: <cause>\nRun '<path> --help' for usage.` line once from dispatch's arg-rejection branch, **gated on `executed.SilenceErrors`** so commands that let cobra print (the root sets only `SilenceUsage`, so `version`/`roles` print via cobra) don't double-print.
- **Suggested action**: (1) surface a silenced command's *pre-`RunE`* failures (arg validation, pre-action flag checks) at the single authoritative classification site, not in the validator. (2) **A predicate the framework calls AND your own code re-calls must be side-effect-free** — printing/logging/mutating in a cobra `Args` func (or any validator re-invoked for classification) duplicates the side effect; put it at the one site that runs once. (3) **Test the message AND its count:** assert `strings.Contains(output, …)` on the operator-facing text (here `accepts at most 1 arg` + `--help`) so the silent-exit path can't return, AND assert `strings.Count(output, …) == 1` so the double-print can't return — the round-3 test checked only `Contains`, which passed against the double-print. General rule for silenced cobra commands: every operator-triggerable error needs a test pinning *some* stderr output and its exact count, because `SilenceErrors` makes both "no message" and "doubled message" passing-looking failure modes.

### 2026-06-03 — new scenarios in the shared feature file must reuse the existing step vocabulary
(Found during PR #7 review of [004-exit-code-convention](../../specs/004-exit-code-convention/tasks.md))

- **Type**: convention
- **Location**: `features/no-runnable-cli/` (the shared problem-driven directory — one per-capability feature file per CLI-Skeleton spec, all wired to one godog step set); step definitions in `internal/cli/dispatch_bdd_test.go`.
- **Severity**: low — no behavior impact, but novel step phrasing forces the Builder to write duplicate godog bindings for assertions that already exist, and clutters the shared file.
- **Description**: the `features/no-runnable-cli/` files accumulate scenarios across specs (001–004 so far, one capability file each), all wired to one godog step set. godog matches steps by exact text, so phrasing that merely rewords an existing assertion silently demands a *new* binding for the same check — e.g. `dispatch will classify…` vs the existing `it will classify the outcome as a usage error`; a combined `route to a help outcome classified as success` vs the existing split `route to a help outcome` + `the outcome will be a success`; `…command whose action completes its work is registered` vs `…command is registered at the top level`. Copilot flagged four such cases on PR #7 (all accepted). Only genuinely-new assertions (004's `Then the process will exit with code N`) legitimately need new bindings. Two further rules surfaced: (1) keep feature wording **implementation-agnostic** — "runtime default status 2" leaked Go-runtime detail into a file whose own `@validation` scenario forbids naming implementation tech; use plain `code 2`; and (2) make repeated assertions **uniform** (`it will not exit with code N`, not a mix of `will never` / `will not`) so they share one parameterized binding.
- **Suggested action**: before adding scenarios to a shared feature file, grep the existing step registrations (`sc.Step(` in the `*_bdd_test.go` for that package) and phrase Given/When/Then to match an existing step whenever the assertion already exists; reserve new phrasings for genuinely new behavior. Keep step text behavioral and tech-agnostic, and keep repeated assertion wording identical so one regex binding covers all instances. **Match the exact anchored regex, including prefixes — approximate vocabulary is not enough** (PR #7 round 2): round 1's fix changed `route to a help outcome classified as success` to `dispatch will route to a help outcome`, but the registered step is `^route to a help outcome$` (no `dispatch will` prefix), so it *still* needed a new binding. The existing 002 pattern is `dispatch will resolve to the "X" group` + `route to a help outcome listing "..."` + `the outcome will be a success` — copy a working multi-step sequence verbatim from a sibling scenario rather than reconstructing it. **Also sweep the source `# Source:` / `# Proposed:` comments for the same tech-agnostic rule** — round 1 fixed the step text `runtime default status 2` → `code 2` but left the matching scenario comment saying "runtime default 2", which round 2 then flagged (symmetric-site miss). The reliable check is to run the godog suite (or `--dry-run`) so unbound steps surface as missing-definition errors instead of waiting for a reviewer.

### 2026-06-04 — a resolved command had no way to emit a UsageError; 006 added a typed-error seam to dispatch
(Found during [T004](../../specs/006-credential-storage/tasks.md) implementation)

- **Type**: design-issue
- **Location**: `internal/cli/dispatch.go` (`Run` default arm) + `commandUsageError`; produced by `internal/cli/authcmd.go` (`runLogin`).
- **Severity**: medium — without it, the interface-cli mapping for Credential Storage (no-token / blank / existing-no-overwrite → `UsageError`/code 2) was unreachable: dispatch mapped every resolved-action error to `RuntimeError`/code 1.
- **Description**: through 002/004, the only `UsageError` sources were cobra-level — unknown command/flag (flag-error hook, non-runnable-node resolution, synthesized nested-group token) and a leaf's own `Args` validator rejection. A *runnable* leaf whose action returned an error was always classified `RuntimeError` (the default arm). But 006's `auth login` must classify several **invocation** faults its action only discovers at runtime (no token resolvable from any source; a blank token; an existing credential with no `--overwrite`) as `UsageError`. An `Args` validator can't express these (they depend on stdin/TTY/env/existing-file state, not positional args). Resolution (ADR-5/DECISIONS): a small unexported `commandUsageError{err}` wrapper that a resolved action returns; dispatch's default arm does `errors.As(err, &*commandUsageError)` *after* the `ValidateArgs` re-check and returns `UsageError` for it, else `RuntimeError`. The leaf sets `SilenceErrors`/`SilenceUsage` and writes its own cause+next-step message (path only, never the token), so the wrapped error is for classification, not display.
- **Suggested action**: **Request Authentication (007)** and any future command that distinguishes operator-fixable invocation faults from internal failures should return `commandUsageError` for the former rather than inventing a parallel mechanism or a second exit-code path — the category→code mapping stays in the single `ExitCode` registry (004). If 007's API client adds the reserved operational categories (APIError/Permission/RateLimited/Network, codes 3–6), those are a *different* axis (the client classifies them into the `Outcome` enum directly); `commandUsageError` is only the command-action→`UsageError` bridge. Pin any new command-originated category with a focused dispatch test (see `TestRun_CommandUsageError_IsUsageErrorCategory`).

### 2026-06-04 — an error-classifier helper must discriminate every typed source and scope its claims
(Found during PR #16 review of [006-credential-storage](../../specs/006-credential-storage/tasks.md))

- **Type**: design-issue
- **Location**: `internal/cli/authcmd.go` (`classifyAuthError`), consumed by `runLogin`.
- **Severity**: low — wrong-but-not-dangerous operator message; no behavior or exit-code impact.
- **Description**: `classifyAuthError` originally branched on `*auth.FormatError` and treated *everything else* as a "write error … the filesystem is unchanged". Two callers feed it errors that are neither: (1) the pre-write guard's `auth.ReadCredentialsFile(target)` returns a wrapped *read* error for an unreadable existing file — reported as a "write error / check write permission" though no write was attempted; and (2) the interactive "both" choice writes multiple targets in a loop, so a failure on a later target occurs *after* an earlier target was already written and its "Stored…" line printed — making the global "filesystem is unchanged" claim false. Fix: three branches — `*FormatError` (not overwritten), `*auth.WriteError` (claim scoped to the single path: the atomic temp+rename guarantees *that path* was not partially written; no global filesystem claim), and any other error reported as a read/access failure naming the path. Copilot caught it in round 1.
- **Suggested action**: when a single helper maps several error sources to one operator-facing message, **discriminate every typed error the producers can return (`errors.As` per type), not just the one obvious type** — a catch-all "else" silently mislabels the others. And **scope state claims to what the code actually guarantees**: an atomic single-file write guarantees only *that file* is intact, so a per-target loop must not claim the whole filesystem is unchanged. The `auth` package already exposes `FormatError`/`WriteError` precisely so callers can tell them apart — use both. Companion to the user-level "throw a named error class so the catcher can discriminate" learning: this is the receiving end (the classifier must actually branch on each type).
- **Producer-side mirror (round 5):** a classifier can only be as accurate as the typed errors it is handed — so the **producer must emit the accurate type at the error's origin**. `WriteCredentials` wrapped a *pre-write* `os.ReadFile` failure (permission denied, or a directory at the path — anything but not-exists) as `*WriteError`, even though no write was attempted. That mislabels at the source: a downstream classifier branching correctly on `*WriteError` would still print "write error" for what is really a read/access failure. Fix: return 005's `*ReadError` from that branch, so the type matches the operation that actually failed and the CLI's `classifyAuthError` read branch ("could not read … no changes were made") fires. **Rule: name a returned error after the operation that failed, not the operation the function is named for** — a writer that fails while *reading* its existing input returns a read error, not a write error. Round 1 fixed the consumer; round 5 fixed the producer feeding it. When auditing typed-error flows, walk both ends: every `errors.As` branch in the classifier AND every `return &XxxError{...}` site in the producers, confirming each names the operation that genuinely failed.

### 2026-06-04 — a writer of a shared file must honor the reader's multi-entry resolution rule
(Found during PR #16 review of [006-credential-storage](../../specs/006-credential-storage/tasks.md))

- **Type**: design-issue
- **Location**: `internal/auth/write.go` (`mergeTokenLine`); reader is `readCredentialsFile` (005).
- **Severity**: medium — a write could silently leave the *old* token effective and leave the stale secret on disk.
- **Description**: the shared reader is **last-`token=`-wins** (`if key == tokenKey { token = value }` over all lines). `mergeTokenLine` replaced only the *first* `token=` line and `break`ed. On a file with two `token=` lines, the write updated the first while the reader returned the second (old) value — the new token never took effect, and the old secret stayed in the file. The single-token round-trip test didn't exercise it. Fix: replace the first token entry in place and **drop every later `token=` line**, collapsing to one entry; added a multi-token regression test.
- **Suggested action**: when a writer edits a file a separate reader parses, **pin the reader's conflict-resolution rule for duplicate keys and make the writer converge on the same effective value** — last-wins reader ⇒ the writer must ensure the surviving/last entry is the new one (collapsing duplicates is the safe move; it also avoids leaving stale secrets). Test the duplicate-key case explicitly: a happy-path single-entry round-trip will not catch the divergence. Companion to the shared-format-module / round-trip DECISIONS.

### 2026-06-04 — validate the bytes you act on, not a re-read: share one parse step between read and write
(Found during PR #16 round 4 review of [006-credential-storage](../../specs/006-credential-storage/tasks.md); code in `internal/auth/credentials.go`, `internal/auth/write.go`)

- **Type**: design-issue
- **Location**: `internal/auth/write.go` (`WriteCredentials`) and `internal/auth/credentials.go` (`readCredentialsFile` → `parseCredentials`).
- **Severity**: medium — a check-then-act TOCTOU: the "malformed → no write" guarantee was validated against a *different* read of the file than the one being merged.
- **Description**: `WriteCredentials` did `existing, _ := os.ReadFile(path)` (the bytes it merges), then called `readCredentialsFile(path)` to validate — which **re-reads the file from disk**. Validation and merge thus operated on two snapshots; a concurrent edit between the two reads could let a malformed file into the merge output (or reject a now-valid one), and it doubled the I/O. The reader-vs-writer "don't drift" intent (ADR-1) was honoured at the *function* level (both call the shared reader) but violated at the *byte* level (different reads). Fix: extract `parseCredentials(path, data []byte)` — the shared, **I/O-free** parse step. `readCredentialsFile` reads then parses; `WriteCredentials` parses the already-read `existing` bytes it is about to merge. One snapshot, one read, no race. Bonus: a pure parse step can only return `*FormatError` (no `*ReadError`), which simplified the writer's error handling.
- **Suggested action**: whenever a function reads bytes, validates, then writes/transforms those bytes, make validation and the action consume the **same in-memory snapshot** — never re-open/re-read between check and act. The clean factoring is a pure `parse(data)` / `validate(data)` helper that takes bytes (or an `io.Reader`), with the single `os.ReadFile` at the boundary; both the read path and the write path call the pure helper. Re-reading "to be sure it's still valid" is the classic TOCTOU anti-pattern — it widens the race window instead of closing it. Generalises beyond files to any check-then-act over mutable shared state.

### 2026-06-04 — harden the credential command's input path: reject newline-bearing tokens, bound piped stdin
(Found during PR #16 review of [006-credential-storage](../../specs/006-credential-storage/tasks.md))

- **Type**: design-issue
- **Location**: `internal/cli/authlogin.go` (`usableToken`), `internal/cli/authlogin_seam.go` (`gatherInputs`).
- **Severity**: low–medium — a crafted token could inject extra `.glassfrogrc` keys; an unbounded pipe could exhaust memory.
- **Description**: (1) `usableToken` trimmed only surrounding whitespace, so a token containing an embedded `\n`/`\r` (from stdin/env/prompt) would be written verbatim into the line-structured `.glassfrogrc`, splitting into multiple lines and injecting keys (e.g. `abc\nevil=value`). Now rejected as unusable → UsageError. (2) `gatherInputs` used `io.ReadAll(os.Stdin)`, reading an arbitrarily large pipe into memory. Now bounded via `io.LimitReader` (64 KiB) with an error past the cap. **(3) Defense-in-depth at the shared API boundary (PR #16 round 3):** the upstream `usableToken` guard was the *only* place the newline rule was enforced, but `auth.WriteCredentials` is a reusable package API that interpolates `token` straight into a `token=<token>` line — a future/other caller passing an unvalidated token would re-open the injection. `WriteCredentials` now rejects `strings.ContainsAny(token, "\r\n")` up front with the exported sentinel `ErrTokenNotSingleLine` and **no write** (the file is left untouched, the token value never appears in the error).
- **Suggested action**: any value written into a **line- or delimiter-structured file** must be validated against the structural delimiters (reject embedded newlines for a `key=value` line format) before persisting — trimming surrounding whitespace is not enough. And **bound reads of external input** (`io.LimitReader`) when the expected payload is small; never `io.ReadAll` an untrusted/unbounded stream. Both are the input-side analogue of the escape/validate-before-interpolate discipline. **Enforce the structural rule at the writer/API boundary, not just at the most-upstream caller**: when a shared helper interpolates a value into a structured format, it must reject delimiter-bearing input *itself* (fail without writing, with a typed/sentinel error and no secret in the message) even when today's only caller validates upstream — the caller's guard protects the caller, not the next caller. Same shape as the "designate a SoT helper and grep siblings" discipline, but applied to a write API: the helper owns its own input contract.

### 2026-06-03 — when triage edits one Score artifact, propagate the decision to its siblings in the same change
(Found during PR #7 review of [004-exit-code-convention](../../specs/004-exit-code-convention/plan.md))

- **Type**: convention
- **Location**: the Score artifact set for a spec (`spec.md` ↔ `plan.md` ↔ `interface-*.md` ↔ `tasks.md` ↔ `validate.md` ↔ feature files) — they restate the same decisions at different altitudes, and `validate.md` additionally *cites the code and tests* by file/line.
- **Severity**: low per round, but it manufactures extra review rounds: a one-sided edit leaves the siblings contradicting the changed file, and the reviewer flags the drift next pass.
- **Description**: PR #7 had two rounds caused purely by incomplete propagation. Round 2 introduced a design decision in `tasks.md` (extract a testable `cli.Main() int`; defer operational categories to `@validation` per ADR-2) but did **not** update `plan.md`. Round 4 then flagged that `plan.md`'s Implementation Strategy, Testing strategy, ADR-4 mechanism, and even the System-Architecture diagram still described the old `os.Exit(cli.ExitCode(...))`-in-`main` approach and a full category↔code one-to-one test — all contradicting the round-2 `tasks.md`. The same applies to the clarify→plan/interface direction (the earlier crash-diagnostic carve-out had to be threaded through spec + plan + interface). A decision lives in several artifacts; changing it in one is a half-edit. **The `code → artifact` direction bites too**: PR #11 changed `resolve.go` during triage (whitespace-only `GLASSFROG_TOKEN` now falls through via `strings.TrimSpace`). Round 2 propagated that to `interface-spec.md` but not to `validate.md`, whose conformance traces still quoted the old `token != ""` predicate — three round-3 comments. The same round's directory-vs-`0o000` test fix removed an assertion that `validate.md` still cited by line (`resolve_test.go:212`), leaving a dangling test reference. A triage **code** fix that changes observable behavior is also a half-edit until the artifacts that *describe or cite* that code (especially `validate.md`'s traces and any `file:line` references) are re-synced.
- **Suggested action**: after changing a decision in any Score artifact **or fixing code during triage**, grep the sibling artifacts in the same spec dir for the old approach (the function name, the mechanism phrase, the predicate like `token != ""`, the test claim, ADR titles, diagram labels, and `file:line` citations) and update every occurrence in the same commit. Treat ADRs, diagrams, "Implementation Strategy / Testing strategy" sections, **and `validate.md` conformance traces / test-line citations** as first-class propagation targets, not just prose. When a triage fix touches code, immediately ask "which artifacts quote this predicate, cite this test line, or describe this behavior?" Cheapest when done proactively — the reviewer will otherwise surface each lagging sibling one round at a time. **Prefer test/function *names* over `file:line` citations in long-lived artifacts** (`validate.md`, learnings): line numbers drift on every edit, and a `grep` for a single stale citation can miss sibling occurrences. PR #11 proved both halves — a `resolve_test.go:212` citation went stale when the directory-test fix removed the assertion, and fixing only the first of *two* occurrences (line 53, missing line 103) cost an extra round; switching to test-name references (`TestReadCredentialsFile_MalformedLineIsFormatError`) removes the drift class entirely. When you must fix a brittle citation, grep the artifact for *every* occurrence of that exact `file:line`, not just the one the reviewer flagged. **Two more drift targets after a plan/tasks *rewrite* (e.g. a conformance pass that changes the task decomposition or resolves a hazard): (a) task IDs** — `analyze.md` and `checklist.md` cite `T00N` by number, so collapsing a 5-task list to 3 (PR #33 conformance to 011) left `analyze.md` K3 saying "T001–T005" and `checklist.md` citing "T003/T004/T005" against a `tasks.md` that now defined only T001–T003; grep `T0\d\d` across the validation artifacts after any re-decomposition. **(b) risk residual states** — when a hazard's control is applied (e.g. H-3's RC-3 next-step fix landed in round 2), update the register *row* (Yellow→Green) **and** the per-hazard detail (drop "currently"/"once applied" framing) in the *same* edit as the residual-summary line; PR #33 left the H-3 row Yellow and the detail pre-fix while the summary said "resolved," giving the implementer contradictory acceptance guidance. The guard re-run refreshes these, but a manual artifact edit must grep the register, the detail, and the summary together. **(c) ordering / superlative claims** — a "first / only / the X-est" assertion written before a sibling spec existed turns false when the sibling lands; scrub it across the *full* artifact set, not just the plan. PR #33 round 2: conforming 012 to 011 removed the "first command to issue a real API call" claim from `plan.md` but left it in the feature-file narrative **and** the `interface-cli.md` intro — Copilot flagged both. ### 2026-06-07 — when parsing an integer that gets scaled into a fixed-width type, bound it against overflow, not just against negative/non-numeric
(Found during PR #43 Copilot review of 017-rate-limit-handling)

- **Type**: code-correctness / parser-robustness
- **Location**: `internal/apiclient/retry.go:parseRetryAfter` (and any future header/config integer that is multiplied by a unit — page sizes, byte counts, timeouts).
- **Severity**: low likelihood (the API sends `Retry-After` ≤ ~3600s), but it silently defeats a safety cap, so worth pinning as a discipline.
- **Description**: `parseRetryAfter` parsed `Retry-After` with `strconv.Atoi` (returns `int` — 64-bit on the build platforms) and returned `time.Duration(secs) * time.Second`. `time.Duration` is `int64` nanoseconds, so any value above `math.MaxInt64 / 1e9` (≈ 9.2e9 seconds ≈ 292 years) overflows when scaled and **wraps to a negative/garbage duration**. The existing guard only rejected `secs < 0` and non-numeric input — it did not catch a *positive* input that becomes negative *after scaling*. A wrapped-negative `wait` then (a) bypasses the total-wait budget check (`waited+wait > MaxTotalWait` is false for a negative wait), (b) makes `time.Sleep(negative)` return immediately, so the loop burns attempts with no real backoff, and (c) prints a confusing negative-duration progress note. The function's own contract ("absent / non-integer / negative / HTTP-date → unusable → fall back to FallbackBackoff") *should* have covered this — overflow is just another flavor of "unusable". Fix: parse with `strconv.ParseInt(v, 10, 64)` (platform-independent) and reject `secs > maxRetryAfterSeconds` (a named `const = int64(math.MaxInt64) / int64(time.Second)`), treating overflow as unusable → fallback. Tests: an overflow case (rejected) and a largest-non-overflowing case (accepted, scaled correctly).
- **Suggested action**: whenever you parse an integer that will be **multiplied/scaled into a fixed-width target** (`time.Duration` ns, a byte count, a millisecond timeout), the validity check must bound the input against the target type's range **after scaling**, not merely reject negativity/non-numeric. The clean shape: derive a named `maxXSeconds`/`maxXBytes` constant from `math.MaxInt64 / int64(scale)` and reject above it, folding "would overflow" into the same "unusable → safe default" branch the parser already has for the other garbage forms. Use `ParseInt(_, 10, 64)` over `Atoi` so the bound is explicit and platform-independent. This is the integer-overflow sibling of the existing URL/semver parser-robustness discipline (a parser must never emit a value that downstream code will treat as a *valid* but nonsensical quantity). 015 (API Error Extraction) and 016 (Pagination) parse their own numeric fields on the same seam — apply the same overflow-bounding there.

### 2026-06-07 — hardening a re-issuing walker over a caller's request: own-the-param means Del-then-Set, guard nil options, and never re-send a consumed Body
(Found during PR #41 Copilot review of 016-pagination — three rounds)

- **Type**: convention / API-boundary hardening
- **Location**: `internal/paging/paging.go` `All[T]` (the per-page query build, the functional-option loop, and the per-page request copy); transferable to any walker/helper that **re-issues a copy of a caller's request struct in a loop** and claims ownership of a subset of its fields, and any functional-option API.
- **Severity**: low–medium — #1 and #3 were latent correctness traps (a partial/wrong request produced silently); #2 a latent panic. None fired in existing tests because the live consumers are well-behaved (bodyless GETs, no stray cursor, no nil option).
- **Description**: a function that loops re-issuing `pageReq := req` (a shallow struct copy) over a caller-supplied `apiclient.Request` shares every field of that struct across iterations — and three of them bit, each caught by Copilot: (1) **`cursor` ownership via conditional Set.** The walker claimed sole ownership of the `cursor` query param but only *conditionally set* it (`if cursor != "" { q.Set("cursor", cursor) }`). The internal `cursor` var is `""` on page 1, so the conditional never fires there — a stale `cursor` in the caller's `req.Query`, copied by `cloneQuery`, **survived into the first request**, starting the walk mid-stream → an apparently-complete result that is actually partial. Ownership of a key you copy from the caller requires an explicit **`q.Del("cursor")`** before the conditional set. (2) **nil functional option.** `for _, opt := range opts { opt(&cfg) }` panics on a nil `Option` (common when a caller appends conditionally); guarded with `if opt != nil`. (3) **consumed `io.Reader` Body.** `req.Body` is an `io.Reader` the first page's `Execute` consumes; the shallow copy shares it, so re-issuing page 2+ re-reads an exhausted reader and sends an empty/partial body — a wrong request, silently. The walker can't rewind an `io.Reader`, so it now **stops loud with a typed `UnrewindableBodyError` before following the next page** when `req.Body != nil` (retaining the page(s) gathered, ADR-3); a single-page body request is unaffected.
- **Suggested action**: when a helper **re-issues a copy of a caller's request struct in a loop**, audit every field of that struct for shared/single-use state, not just the obvious one: (a) **map/slice fields it claims to own** — clone, then `Del`+set each owned key (never a conditional `Set` guarded by an internal "do I have a value yet" flag, which skips the first iteration); test by passing the owned key in the caller's input and asserting the first outgoing request omits it and the caller's map is untouched; (b) **`io.Reader`/`io.Closer`/channel/other single-use fields** — these cannot be safely re-sent; fail loud (typed error, partial retained) when re-issue would be required, rather than send a consumed value; test multi-iteration-with-body stops loud AND single-iteration-with-body succeeds; (c) **functional-option loops** — guard `if opt != nil` and pin with a `nil`-in-the-middle test. (The nil-option guard is distinct from the project's "fail-fast on nil **seam**" rule — that governs required injected dependencies; an optional configurator should be skipped, not fatal.) Meta: all three landed across three review rounds of the SAME PR — a shallow-struct-copy-in-a-loop is a cluster hazard; when you write one, sweep all of its fields for shared state in the first pass.

### 2026-06-08 — a retry/backoff loop with an injected sleep seam must check ctx.Err() before sleeping (time.Sleep ignores context)
(Found during PR #43 Copilot review of 017-rate-limit-handling)

- **Type**: code-correctness / responsiveness
- **Location**: `internal/apiclient/retry.go:(*RetryExecutor).Execute` — the bounded 429 backoff loop; any future loop that waits between attempts (016 Pagination if it ever backs off; a write-retry path).
- **Severity**: low impact (waits are cap-bounded), but a real responsiveness defect for an interactive CLI / cancellable agent run.
- **Description**: 017 injects `sleep func(time.Duration)` (prod binds `time.Sleep`) so cap/backoff tests never block. But `time.Sleep` does **not** observe `context.Context` — so if the caller cancels (Ctrl-C) or the deadline fires *between* a 429 response and the next attempt, the loop still emitted the progress note and slept the full backoff before the next `client.Execute` could fail-fast. The per-attempt `client.Execute` honors ctx (it flows to `http.Do`), but the *gap between attempts* did not. Fix: check `reqCtx.Err() != nil` immediately before the note/sleep and, if set, surface the current outcome unchanged (`return resp, err`) — consistent with the other give-up branches (exhaustion, over-budget). Keeps cancellation responsive without making the injected sleep itself ctx-aware (the seam stays a plain `func(time.Duration)` for hermetic tests). Test: a base that cancels the ctx during its round trip, then returns a 429 → the loop surfaces the 429 with no sleep, no note, exactly one attempt.
- **Suggested action**: any loop that sleeps between iterations behind an injected (ctx-unaware) sleep seam must gate the sleep on `ctx.Err()` — either check before sleeping (minimal, keeps the seam a plain `func(time.Duration)`) or make the wait ctx-aware (`select { case <-time.After(d): case <-ctx.Done(): }`, but that reintroduces real time in tests unless the seam is richer). Prefer the pre-sleep check when the next iteration's first action already honors ctx and will fail-fast. The per-call timeout/cancellation covering the *work* does not cover the *wait between calls* — they are separate windows.
