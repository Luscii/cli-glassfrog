# Decisions

Architectural precedent from the specification pipeline. Each entry records a decision that future specs should follow or explicitly diverge from. Managed by the Score plan skill.

---

- Build the CLI in Go as a self-contained executable (from 001-command-registration, 2026-06-03)
  Chosen over Rust and compiled TS to satisfy CONSTITUTION XII natively (single self-contained binary, no runtime). Foundational language decision inherited by every later spec; built with GOOS/GOARCH cross-compilation and CGO_ENABLED=0 to avoid cgo where supported. ("Fully static" linking is platform-specific and is not the criterion — self-containment is.)

- Adopt cobra as the command framework; its command tree is the command registry (from 001-command-registration, 2026-06-03)
  Sibling capabilities (Argument Dispatch, Help & Version) become thin layers over cobra rather than separate subsystems. Later command specs register into the cobra tree.

- Enforce fail-loud registration through a guard wrapper, not cobra defaults (from 001-command-registration, 2026-06-03)
  cobra tolerates duplicate names and missing summaries; a Register/MustRegister guard validates (non-empty name+summary, leaf-has-action, group-has-children, no sibling collision) before AddCommand. All command registration must go through the guard — direct AddCommand is the bypass to watch.

- Wire commands explicitly in main, not via package init() side effects (from 001-command-registration, 2026-06-03)
  Deterministic ordering and a single legible source of truth for the command set (aligns with CONSTITUTION I). Adding a command = one wiring line + its own package; no existing command is edited.

- Route via cobra's built-in resolution; keep matching exact (from 002-argument-dispatch, 2026-06-03)
  Dispatch relies on cobra's Execute over the assembled tree rather than a hand-rolled matcher: exact match, unknown-command error + best-effort suggestion, and unknown-flag rejection are cobra defaults. cobra's EnablePrefixMatching (a package-global) MUST stay false — prefix/abbreviation matching is a non-behavior; pin it with a regression test.

- Dispatch classifies each outcome into a code-free category for Exit-Code Convention (from 002-argument-dispatch, 2026-06-03)
  Run returns Success / UsageError (two values, matching what the spec names). A distinct RuntimeError for a resolved command's own failure is deferred to Exit-Code Convention (004), the consumer that needs the distinction — until then a resolved command's error is returned uncategorized. Dispatch must NOT emit exit codes (that's 004); the entrypoint maps the category minimally (0 / non-zero) as a documented placeholder.

- Help & Version uses cobra's standard help rendering, not a custom template (from 003-help-and-version, 2026-06-03)
  Listing, per-command usage, flags section, and alphabetical sorting are cobra defaults; future command specs get standard help for free by setting a non-empty Short summary. Alphabetical order depends on the cobra package-global EnableCommandSorting staying true — pin it with a regression test (mirrors 002's EnablePrefixMatching pin). The spec's original "no flags section / no long description" non-behavior was narrowed (clarify 2026-06-03) to forbid only new *required* documentation data.

- Hide cobra's built-in `help` and `completion` commands; keep the `--help` flag (from 003-help-and-version, 2026-06-03)
  cobra injects `help` and `completion` outside the registration guard (LEARNINGS finding). Both *commands* are removed from resolution: replace the default help command with a hidden command under a **non-`help` name** (SetHelpCommand(&cobra.Command{Use: "__help_disabled", Hidden: true})) so the `help` token no longer resolves — `Hidden:true` alone only hides from listings, it does not disable `glassfrog help` — and set CompletionOptions.DisableDefaultCmd=true for `completion`. The `--help` *flag* is retained. Future specs that want a framework built-in surfaced must opt in explicitly.

- Exit codes flow through a single ExitCode(Outcome) registry; 004 is a pure category→code mapper (from 004-exit-code-convention, 2026-06-03)
  `internal/cli/exitcode.go` is the single source of truth: named constants pin the frozen convention 0 success / 1 internal / 2 usage / 3 API / 4 permission / 5 rate-limit / 6 network-unavailable, and `ExitCode(Outcome) int` maps categories with a Fail-Safe default of 1 (an unmapped/future category never yields 0). Producers classify into the `Outcome` category; 004 only maps — it never re-inspects the error (continues 002 ADR-2). Codes 3–6 are published as constants now but the live `Outcome` enum gains a category only when its producer exists; the future API client adds APIError/PermissionError/RateLimited/NetworkUnavailable + their ExitCode cases at this one site, taking the reserved codes. Never renumber an assigned code. Pin uniqueness, the no-shell-reserved range (126/127/128+N), and the exact values with regression tests (mirrors 002/003 package-global pins).

- RuntimeError resolved as the catch-all internal-error code (1); dispatch's default arm reclassified (from 004-exit-code-convention, 2026-06-03)
  002 deferred the distinct RuntimeError category to 004. Resolution: a resolved command whose own action errors is now classified `RuntimeError` (added to the `Outcome` enum, mapped to code 1) — `dispatch.Run`'s default arm returns `RuntimeError, err` instead of `Success, err`. The two deferral tests (`TestRun_RuntimeActionError_IsSuccessCategory`, `TestRun_RuntimeError_NotMisclassifiedAsArgError`) were updated to assert RuntimeError. Until the API client classifies finer, every resolved-command failure exits 1.

- `main` recovers from panics and exits 1 to avoid the Go panic→exit-2 collision (from 004-exit-code-convention, 2026-06-03)
  An unrecovered Go panic terminates with status 2, which collides with `UsageError = 2`. To honor the accord ("unexpected internal failure → 1, never 0/never aliased to usage"), `main` installs a deferred recover that writes the panic value + stack to stderr (Action Transparency) and `os.Exit(1)`. Future entrypoint changes must preserve this recover.

- Token concerns live in a new `internal/auth` package; the credentials-file read and write sides share one format module (from 005-credential-discovery, 2026-06-03)
  Token Authentication's three capabilities split as: Discovery (005) contributes the resolver + the shared `.glassfrogrc` reader; Credential Storage (006) adds the writer to the same package and MUST round-trip with that reader; Request Authentication (007) consumes the resolved credential (it lives with the API client, not in `internal/auth`). Resolution stays out of `internal/cli` — it registers no command and makes no API call (CONSTITUTION V).

- Credentials file format and env var: `.glassfrogrc` npmrc-style `key=value` with a `token` key, and `GLASSFROG_TOKEN` — both `[ASSUMED]` (from 005-credential-discovery, 2026-06-03)
  Hand-rolled minimal reader (no INI/dotenv dependency — CONSTITUTION XII), `#`/blank tolerant, unknown keys ignored (forward-compatible), a non-comment line without `=` is a parse error (not silently skipped). File name + env var are centralized constants and `[ASSUMED]` pending reconciliation with Credential Storage (006) — 006 must conform to or jointly revise this contract before both ship.

- Credential Discovery returns a code-free `Resolution{Token, Source, Path}`; absence is a normal outcome, broken files are errors (from 005-credential-discovery, 2026-06-03)
  Mirrors 002's "resolver classifies, consumer maps" split. `Source` is an enum (`Environment`, `File`, or `None`) with a separate `Path` (the file path when `Source` is `File`, empty otherwise); `None` is a non-error "nothing found"; a read/parse failure of an existing file is a typed error naming the path. The token value never appears in output, logs, or error strings (secret hygiene; CONSTITUTION II). 007 consumes this shape and reports `Source`/`Path` (never the token) as the active identity. No exit codes here.

- Filesystem/env-dependent resolvers inject their start/home roots rather than reading process globals (from 005-credential-discovery, 2026-06-03)
  The pure resolver takes `startDir`/`homeDir` (and reads the env var through a thin seam); a small production wrapper binds the real `os.Getwd`/`os.UserHomeDir`/`os.Getenv`. Keeps unit tests hermetic and — critically, given the secret — guarantees tests never read the developer's real `~/.glassfrogrc` (CONSTITUTION IV).

- The credentials-file writer lives in `internal/auth` beside Discovery's reader; a write→read round-trip test is the format contract (from 006-credential-storage, 2026-06-04)
  Storage adds `writeCredentials(path, token)` to `internal/auth`, sharing the one format module with 005's reader (no second implementation of the `.glassfrogrc` shape). The binding guard is a round-trip test: write a token, resolve it back through Discovery's reader. Because 005 is not yet implemented, whichever of 005/006 lands first creates the shared reader+constants to 005's interface-spec; the round-trip test pins the shape either way. `.glassfrogrc`/`GLASSFROG_TOKEN` stay `[ASSUMED]`, now jointly held — change once, in the shared constants.

- Operator-facing credential/transport concerns stay in their command/client layer; only the file concern lives in `internal/auth` (from 006-credential-storage, 2026-06-04)
  Storage is the first credential *command*: a guard-registered cobra leaf in `internal/cli` (explicitly wired in `main`, with an `Args` validator and a `Short`) that gathers input and delegates the file write to `internal/auth`. Mirrors how 007 will keep request-attachment with the API client, not in `auth` — `auth` stays command- and network-free (CONSTITUTION V). Exact command name/group/flags are interface-level, deferred.

- Connection Configuration lives in `internal/apiclient`; Base URL Resolution is its first capability and produces the base transport's base URL (from 008-base-url-resolution, 2026-06-04)
  Resolves the `[ASSUMED]` seam/package 007 flagged: 007's `AuthTransport` wraps Connection Configuration's base transport, and the resolved base URL is that transport's root. `internal/apiclient` (created by 007) is now the fixed home for connection/transport concerns — base URL, timeouts, retries — NOT `internal/auth` (which stays the credential-file, network-free concern) and NOT `internal/cli` (no command, no API call). The connection-context half (combine base URL + token, assemble the `http.Client`) is a deferred later spec.

- Base URL resolves on the precedence chain flag → env → `.glassfrogrc` `base_url` → built-in default, and always yields a value (from 008-base-url-resolution, 2026-06-04)
  Mirrors 005's env-first walk-up (reuses `candidateDirs` + nearest-wins) but adds a `--base-url` flag rung on top and a compile-time default backstop at the bottom — so, unlike 005's `Resolution`, there is NO `None`/absent outcome. Result is a code-free `BaseURL{Value, Source, Path}` with a `Source` enum (`Flag`/`Environment`/`File`/`Default`), continuing the 002/004/005/007 "producer classifies a code-free outcome, consumer maps it" split. A non-empty source supplying a non-`http(s)` URL is a typed code-free `BaseURLError` naming the source (no fall-through, fail loud); whitespace-only / absent key falls through; the default is never re-validated. Open downstream gap (mirrors 007's): 004 has no "bad configuration" code (code 4 is API-side) — the consuming-command spec decides.

- A second `.glassfrogrc` key (`base_url`) is read through 005's one shared reader, never a parallel parser; the token is never returned to non-secret callers (from 008-base-url-resolution, 2026-06-04)
  `internal/auth` exposes a network-free, secret-safe `base_url` file read over the existing `candidateDirs` walk + `parseCredentials` step, returning only the `base_url` value (+ path), never the token — so base-URL code paths never hold the secret. No second `.glassfrogrc` reader is written (LEARNINGS: two readers of one file drift). The `base_url` file-key constant lives in `auth` beside `tokenKey` (a format detail); `GLASSFROG_BASE_URL`, the `--base-url` flag name, and the default URL are `internal/apiclient` constants. The three names (`base_url`, `GLASSFROG_BASE_URL`, `--base-url`) are `[ASSUMED]`, jointly held with Credential Storage (shared file); the default URL is a fixed constant `https://glassfrog.com/api/v5` — the `/api/v5` path from the spec's `servers` block, the host `https://glassfrog.com` *inferred* from `info.contact.url` (not normatively specified by the OpenAPI spec; see risk H-1). `auth`'s scope broadens honestly from "the token" to "the `.glassfrogrc` file" while staying network- and command-free.

- Request Authentication is an `http.RoundTripper` middleware wrapping Connection Configuration's base transport; lives in the API-client package, consumes (never re-resolves) Discovery's `Resolution` (from 007-request-authentication, 2026-06-04)
  007's auth layer wraps the base transport so the base is reached only on the authenticated branch — "no request is ever sent unauthenticated" becomes structural, not caller discipline. It holds an injected `func() (auth.Resolution, error)` (prod = 005's resolver) and maps the outcome to a typed, code-free `AuthError{Kind}` — `NoCredentials` (Discovery `Source: None`) vs `CredentialError` (wraps Discovery's path-only read/format error); the consuming command does `errors.As` and maps to an exit code (007 decides none, continuing 002/005's producer-classifies/consumer-maps split). Code lives in the API-client package (`internal/apiclient` `[ASSUMED]`), NOT `internal/auth` (keeps auth network-free). The composition seam with Connection Configuration and the package name are `[ASSUMED]` — reconcile before either ships (parallel session); whichever of 007/Connection-Configuration lands first creates the package (mirrors 005/006). Open downstream gap: 004's frozen convention has no local "cannot authenticate" precondition code (code 4 is API-side rejection) — the consuming-command spec must decide.

- Interactive-input commands inject the stdin/TTY/env/dir seam, same as filesystem resolvers (from 006-credential-storage, 2026-06-04)
  Extends 005's injected-roots rule to the input side: a pure resolver takes the candidate sources (positional arg, stdin reader, an `isTTY` flag, env lookup) + `startDir`/`homeDir`; a thin production seam binds real stdin/TTY/`os.Getenv`/dirs and the non-echoing prompt. A single `isTTY` signal drives both "read piped stdin" and "prompt only when interactive". Keeps every precedence/interactivity branch hermetically testable and tests off the real terminal and home.

- The generic `.glassfrogrc` read/parse/walk lives in `internal/rcfile`; `auth` and `apiclient` are consumers (refactor, 2026-06-06)
  Supersedes the placement in 005 ADR-1 / 006 / 008 ADR-3 that put the shared `.glassfrogrc` reader, parser, and `candidateDirs` walk in `internal/auth`. Those decisions were right that there must be **one** reader (no parallel parser); they were wrong to home it in `auth`, which is the *token/secret* concern — the file format, the `key=value` parse, the nearest-wins walk, and the typed `FormatError`/`ReadError` are generic and have multiple consumers (token, base URL, future settings). `internal/rcfile` now owns them: `FileName`, `Settings`+`Value(key)`, `Parse`, `Read`, `ReadValue(path,key)`, and `Resolve(startDir,homeDir,key)` (the one walk). Every setting is retrieved through this one parameterized path, so consumers can't drift. `internal/auth` keeps the token domain (`Resolution`, `Source`, env short-circuit, the writer, secret hygiene) and re-exports `FormatError`/`ReadError` as type aliases for its credential-command consumers; the `token` key stays in `auth`, the `base_url` key moves to `apiclient` (each domain owns its key). Secret hygiene becomes structural: `rcfile.Resolve(…, baseURLKey)` returns only the base_url value, so a base-URL read can never come into possession of the token. `auth.ResolveBaseURLFile` (008) is deleted — `apiclient` calls `rcfile.Resolve` directly. Future consumers add a key constant in their own package and call `rcfile.Resolve`/`ReadValue`; they never write a second parser.

- Secret files are written atomically (temp-in-same-dir + chmod 0600 before bytes + rename) and merged line-preserving (from 006-credential-storage, 2026-06-04)
  An existing credentials file is parse-validated via the shared reader (malformed → format error, NO write), then rewritten at the line level — replace the `token=` value, append if absent, preserve every other line and comment. The write is atomic: a temp file in the same directory, `chmod 0600` (`[ASSUMED]`, POSIX-conditional) before any token bytes, then `rename` over the target — so a mid-write failure leaves the original intact and the secret is never briefly world-readable. Storage emits a code-free `Outcome` (UsageError for no-token/no-override, RuntimeError for write/format failures) mapped by the existing `ExitCode` site; no new codes, no `os.Exit` in the command (continues 002/004/005).

- Connection Context Assembly is a transparent aggregator: `Assemble` calls 008's and 005's resolvers once and always returns a code-free `ConnectionContext` carrying both outcomes (incl. errors) (from 009-connection-context-assembly, 2026-06-06)
  The connection-context half 008 deferred. `internal/apiclient`'s `Assemble(resolveBaseURL, resolveCred) ConnectionContext` invokes BOTH injected resolvers (no short-circuit on the first error — carry-both), packs `BaseURL`+`BaseURLErr` and `auth.Resolution`+`CredErr` verbatim, and returns the context with NO `error` of its own — assembly never fails, never refuses, decides no exit code (continues the 002/004/005/007/008 producer-classifies/consumer-maps split). Readiness is derived (`Complete()` = base URL present AND token present (`Source != None`) AND no errors), reported not decided. The refuse-to-call fail-safe stays in 007. Purely additive (`context.go`); no existing file changed. `AssembleFromOS(flagValue)` binds the real resolvers; the pure `Assemble` takes injected seams (005/008 ADR-5 pattern), fail-fast on nil (no nil-default — PR #20). Client assembly (the `http.Client`/base transport) is NOT here — it moves to Request Execution (010), refining 008's "connection-context half assembles the http.Client" forecast.

- The connection context is the single resolution point and carries the token; Request Execution (010) replays it into 007's `AuthTransport` rather than re-resolving — resolves the 007/009 `[ASSUMED]` seam (from 009-connection-context-assembly, 2026-06-06)
  `ConnectionContext` carries the full `auth.Resolution` (token included), so resolution happens once per invocation, at assembly. 010 will build `NewAuthTransport(baseTransport, func() (auth.Resolution, error) { return ctx.Cred, ctx.CredErr })` — a replay thunk over the context's cached credential, NOT a fresh Discovery walk — so identity+endpoint are stable across calls by construction and the two walks can't drift. 007's `authorize` still yields the token on the present branch and the typed `AuthError` (`NoCredentials`/`CredentialError`) on the absent/errored branches, so 007's fail-safe refusal fires at request time, unchanged — 007's code is untouched by 009 (the wiring lives in 010). Because the context holds a secret, it gets a value-receiver redacting `String()` (the `auth.Resolution.String()` precedent); readiness reasons are source/path-only, never the token. Settles the seam both 007 and 008 flagged `[ASSUMED]`; consider `/score:deprecate` to retire the open seam note.

- The API-client seam is a `Client` built once from the `ConnectionContext` via `NewClient(ctx, base) (*Client, error)` (with a `NewClientFromOS(ctx)` production seam binding the real base transport); `(*Client).Execute` is the single send seam (from 010-request-execution, 2026-06-06)
  Realizes the `http.Client` 008 forecast and 009 deferred. `internal/apiclient`'s `NewClient(ctx ConnectionContext, base http.RoundTripper)` (and its thin `NewClientFromOS(ctx)` production seam that binds the real base transport) is built ONCE per invocation (the context is already resolved once at assembly) and holds the configured `*http.Client` (base transport + 007's `AuthTransport` over the replay thunk + a request timeout); endpoint commands call `(*Client).Execute`, never a hand-built client — that is the "every command reinvents transport plumbing" problem this capability kills. 011–017 depend on this seam. Purely additive in `internal/apiclient`; no existing file changed; registers no cobra command (prints nothing, no `os.Exit`). The exact `Client`/`Execute`/request-descriptor API is interface-level (`/score:interface`).

- 010 owns the base-URL fail-fast (in `NewClient`); the token fail-safe stays in 007's `AuthTransport` at send time (from 010-request-execution, 2026-06-06)
  Resolves spec fork A (option b). `NewClient` returns `ctx.BaseURLErr` verbatim and builds nothing when the endpoint is missing/errored (010's own concern — fail loud at the source, not as a doomed wire call); it does NOT inspect the token. It wires `NewAuthTransport(base, func(){ return ctx.Cred, ctx.CredErr })` (009 ADR-2's replay thunk), and 007's `authorize` refuses at `RoundTrip` time on the absent/errored credential — so the two refusals stay split (no-endpoint = build-time/010; no-token = send-time/007) and the `NoCredentials`/`CredentialError` taxonomy is never re-decided outside 007. 007's code is untouched.

- The API client produces typed code-free errors (`TransportError`, generic non-2xx `ResponseError{status,headers,body}`, `DecodeError`); the consuming command adds the `Outcome` cases and maps them — `apiclient` never imports `internal/cli` (from 010-request-execution, 2026-06-06)
  Continues the producer-classifies/consumer-maps split (002/004/005/007/008/009) and refines 004's "the API client adds APIError/PermissionError/RateLimited/NetworkUnavailable + their `ExitCode` cases" forecast: the *client* (010) produces the typed errors but wires NO exit code (it has no command and no exit path); the first consuming *command* (011) does `errors.As` and adds the `Outcome` categories + `ExitCode` cases at `internal/cli`'s single registry, taking the reserved codes (transport → 6 network-unavailable; non-2xx → 3/4/5 once 015/017 classify). 010's non-2xx `ResponseError` is GENERIC and carries status+headers+body so 015 reads the detail and 017 reads the 429 rate-limit headers off the same value (010 never interprets or retries — one bounded `Do` with a timeout, no retry; 017 layers backoff above the seam). `errors.As(err, &authErr)` runs BEFORE wrapping a `Do` error so 007's fail-safe is propagated unchanged rather than mislabeled as transport. 010 never reads `ctx.Cred.Token` — the replay thunk is the token's only path.

- API response models live in a new `internal/glassfrog` schema package; the read commands decode into shared types, never command-local duplicates (from 011-identity-read, 2026-06-07)
  Resolves Q1. The `GET /me` (and every later read) body decodes into plain JSON-tagged structs in a NEW `internal/glassfrog` package — `MeResponse{Actor,Organization,Membership,Roles []Role}`, `Actor{ID,Name,Kind}`, `Organization{ID,Name}`, `Membership{AccessLevel,…}`, and a minimal `Role{ID,Name}`. Schema only — no transport, no cobra, no exit codes — so it is a leaf package both `internal/cli` and `internal/apiclient` import without a cycle, keeping `apiclient` transport-only (010) and `cli` free of domain types. `Role` is shared from day one: `me --include roles` decodes it AND My Roles (012) decodes it (012 grows the SAME type to the full role shape — accountabilities/domains/assignments — never a second type). 012–017 add their resource models (Action, Project, Proposal, …) here. Decoding is tolerant of unknown/extra fields (forward-compatible). The token is never a field (it is a request header, not a response field).

- `--base-url` registers as a persistent flag on the root command; API commands read it by cobra inheritance, not by re-registering (from 011-identity-read, 2026-06-07)
  Resolves Q2 and closes the "first consuming command registers the flag that triggers a real call" gap 008/010 forecast. The `--base-url` flag (name from the existing `apiclient.FlagBaseURL="base-url"` constant, so the precedence rung and the registered flag name can't drift; the usage/help string is an implementation detail kept consistent with the spec) is registered ONCE as a persistent flag on the root in the wiring layer; `me` and every future API command (012–017, proposals) read its resolved value via inheritance and pass it to `AssembleFromOS(flagValue)`. One definition for the whole CLI, no per-command duplication; global connection options live at the root. Cost: root help now shows a global-flags section (the affected 003 help tests are updated in the same change; permitted — 003's narrowed non-behavior forbids only new *required* documentation data, and a persistent flag with a description is optional) and the flag appears (inert) on non-API commands like `version`/`auth` (accepted).

- The read surface classifies 010's typed client errors through one `internal/cli` helper into the `Outcome` enum; 011 adds the operational categories + `ExitCode` cases at the single registry (from 011-identity-read, 2026-06-07)
  011 is the first consuming command, so it populates the codes 004 reserved: it adds `NetworkUnavailable` and `APIError` to the `Outcome` enum (`dispatch.go`) and their cases to `ExitCode` (`exitcode.go`), taking reserved codes 6 and 3, and introduces a shared `classifyClientError(err) Outcome` (`internal/cli`) — the single `errors.As` chain over 010's typed errors — reused verbatim by 012–017 (no per-command inlined chains). `ExitCode` stays a pure mapper (the classifier produces the category; `ExitCode` only maps; `default→1` fail-safe unchanged). The mapping (ADR-4): `*TransportError`→`NetworkUnavailable`(6); generic non-2xx `*ResponseError`→`APIError`(3, the residual "general API error" bucket — 015/017 later SPLIT 401/403→permission(4) and 429→rate-limit(5) as new cases WITHOUT renumbering 3); `*AuthError{NoCredentials}`→`UsageError`(2, "not authenticated — run `glassfrog auth login`", mirroring `runLogin`'s no-token→Usage); `*AuthError{CredentialError}`/`*DecodeError`→`RuntimeError`(1, mirroring `runLogin`'s FormatError→Runtime); base-URL error→`UsageError`(2, operator-supplied bad endpoint). No new exit codes invented — local/precondition failures reuse 1/2; reserved 3–6 are for genuine API-side/network outcomes. The classifier table test carries an exhaustiveness guard (PR #10 LEARNINGS: `len`+comma-ok so a dropped mapping fails loud).

- Each read command pairs a pure `run<Read>` + a pure `format<Read>` projection renderer behind an injected seam; the reshaped projection is the agent-legible default, `--output json` a future flag (from 011-identity-read, 2026-06-07)
  Extends 006's `runLogin`/`loginSeam` pattern to the read surface: a thin cobra `RunE` over an injected seam (prod binds `AssembleFromOS`/`NewClientFromOS` + the real base `http.RoundTripper`; tests bind a fake transport returning canned responses) delegating to a pure `runMe(cfg)` over injected values, with a pure `formatMe(MeResponse) string` projection renderer and a pure `validateInclude([]string)` that rejects an unsupported `--include` target BEFORE any request (fail-fast usage error, 002 invalid-input convention). Every branch (success-decode, non-2xx, transport, no-token, decode-fail, base-URL-error, include-rejection, roles-embed, empty-roles) runs offline; a tripwire fake asserts no request is issued on include-rejection. `formatMe`/`validateInclude` are unit-tested pure. Command-level scenarios become a NEW `internal/cli` godog suite (the `credstorage_bdd_test.go` pattern) pointed at its OWN feature file `features/self-service-reads/identity-read.feature`. The reshaped projection (actor id/name/kind, org id/name, membership access level; roles id+name when embedded) is the default; structured `--output json` is a deferred future cross-cutting flag (a Non-Behavior here).

- My Roles (012) conforms to Identity Read (011)'s landed self-service-read scaffolding rather than creating its own (from 012-my-roles, 2026-06-07)
  011 landed first and owns the shared scaffolding, so 012 (a parallel session) conforms — the "other conforms" half of the first-to-land rule (005/006, 007/008). `glassfrog me roles` (`GET /me/roles`) is a `NoArgs` subcommand registered under 011's **runnable** `me` command (a command that both runs and parents children — confirm the 001 guard permits this); it inherits the persistent root `--base-url` (011, name from `apiclient.FlagBaseURL`), routes 010's typed errors through 011's shared `classifyClientError` (adding NO new `Outcome` category and NO `ExitCode` edit), and **grows the shared `internal/glassfrog.Role`** (adds Purpose/Accountabilities/Domains) plus a `MyRolesResponse{Data,Meta{Pagination}}` wrapper — never a command-local type.
