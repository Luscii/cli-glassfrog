# Composed-leaf registry — the commands the Proposal Circulation Path composes.
#
# THE single source of "which glassfrog leaves the circulator composes", consumed
# by:
#   - the proposal-circulator agent  (plugin/agents/proposal-circulator.md)
#     — its "Composed commands" section names exactly these leaves and no others
# so the artifact prose and this registry can never disagree about the composed
# surface or its gate posture (mirroring the write-safety gate's
# gated-commands.txt, plugin/hooks/gated-commands.txt, and the sibling
# composed-leaf registries in plugin/agents/).
#
# Each non-comment, non-blank line is ONE `glassfrog` leaf the circulator may
# invoke, written as the two-token `<group> <sub>` pair (matching how the
# write-safety gate's registry writes its `proposal <sub>` leaves, so the two
# read like with like). Two are grounding/situating reads (proposal get, proposal
# list); two are the gated bodyless governance transitions the write-safety gate
# confirms by design (proposal propose, proposal withdraw), each run only through
# the confirmed write flow and each confirmed independently. No other proposal
# write ever appears here — the path never creates a proposal (that is the
# proposal-drafting path) and never records a response (that is the
# proposal-impact-review path).
#
# The gate posture this registry promises holds only while `proposal propose`
# and `proposal withdraw` are EACH listed in the write-safety gate's registry
# (plugin/hooks/gated-commands.txt) and the two reads are absent from it — so a
# rename or drop in the CLI, or an edit to either registry's membership, means
# revisiting both files and the agent artifact together; the artifacts must
# never name a command the CLI lacks or a transition the guardrail stops
# confirming.
proposal get
proposal list
proposal propose
proposal withdraw
