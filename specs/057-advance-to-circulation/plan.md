## System Architecture

Advance to Circulation is the **`propose` transition leaf of the `proposal` family** — architecturally the meeting point of two landed-by-sibling patterns: the bodyless write leaf of Tension Discard (045) and the `proposal` group + `glassfrog.Proposal` model + singular `proposal` render path of Proposal Reads (056). It introduces **no new transport, model, render, or error machinery of its own**: it sends one **bodyless** `POST /proposals/{proposal_id}/propose`, decodes the returned `{data: Proposal}` document, and renders it through the same flow `proposal get` uses. It adds **no `internal/glassfrog` change** (the `Proposal` model is 056/055's) and **no `internal/render` change** (the singular `proposal` view/templates are 056/055's) — its only new surface is one cobra leaf and its pure `run` function.

Because **no proposal code exists yet** in the base (neither 055 Proposal Creation nor 056 Proposal Reads has landed), 057 is a pure *consumer* of three sibling-owned artifacts — the `proposal` group (`newProposalCommand`), the `Proposal` model, and the singular `proposal` render path. It follows the same **first-to-land-creates / follower-reuses** coordination 056 documented for its relationship to 055 (and 043 to 042): 057 is overwhelmingly likely to be a follower (056 is already Analyzed, 057 just Specified), so it attaches its leaf to the existing group and reuses the model and render unchanged; if it somehow lands first it creates the minimal subset it needs (see Risks). It adds **no new `Outcome`/`ExitCode`**.

Three properties of `proposeProposal` shape the flow, and all three are decided below. First, the request is a **bodyless POST to a sub-resource path** — `Method: http.MethodPost`, no `Body`, `ContentType` left `""` (no `Content-Type` header, exactly as discard's `DELETE`), `out` a `*Document[Proposal]` — combining createTension's POST+decode (`tension.go:182`) with discard's empty-body shape (`tension.go:443`). Second, the success carries a **real payload** — the advanced `Proposal` (now `proposed_outside_meeting`, with `response_deadline`, the implicit `no_objection` in `response_summary`, and updated `available_transitions`) — so unlike discard the command **decodes and renders the server's proposal**, it does not synthesize a result (ADR-2). Third, the transition is **server-authorized** — allowed only when `propose` is in `available_transitions`, enforced by the server with a `422` — so the command issues the `POST` and lets the server decide, and treats a `422` (transition not allowed) and a `404` (no such proposal) as **real failures**, never folding them into success the way discard folds its `404` (ADR-3).

**Components**:

- **`internal/cli/proposal.go`** (extended, by a sibling) / a new `proposal_propose.go` — a `propose <prp-id>` leaf attached to the `proposal` group (`newProposalCommand`, 056 ADR-1), beside `list`/`get` (056) and `create` (055). `cobra.ExactArgs(1)` over the `prp_` id; **no flags** beyond the inherited persistent `--base-url`/`--output` (a transition has nothing to edit), so a stray flag is cobra's own unknown-flag `UsageError(2)` (the structural guard 045/056 rely on). It delegates to a pure `runProposalPropose(cfg)` over the **`proposalSeam`** a sibling lands, so every branch (success, transport, non-2xx, not-authenticated, bad-`--output`) runs offline against a fake transport. The group `Short` widens to name `propose`.
- **No `internal/glassfrog` change** — the `200` decodes into the sibling-owned `Document[Proposal]`; no model field is added.
- **No `internal/render` change** — the advanced proposal renders through the sibling-owned singular `proposal` path (`ProposalView` + `ResourceProposal` + `proposal.{full,compact}`) for human output, and `output.RenderSuccess` over the raw `{data: Proposal}` bytes for `json`/`yaml`.

**Data flow**: `propose <prp-id>` → resolve render target (020/035); a bad `--output` is a fail-fast `UsageError(2)`, no request → `assemble` (009) → `newClient` (008/007) → `NewRetryExecutor` (017) → one `Execute` `POST /proposals/{prp_id}/propose`, **no body, no `Content-Type`**, `out == &Document[Proposal]` (010) → branch on the outcome:
- `err == nil` (a `200`): success — render the decoded/raw proposal and exit `Success(0)`.
- any error: `reportFailure` → `refineClientError`/`classifyClientError` (015/017) maps transport → `NetworkUnavailable(6)`, `401`/`403` → `PermissionError(4)` (the Premium `403` included — no plan-gate special-casing, ADR-3), `429` → `RateLimited(5)` (a `POST`, so 017's `isSafeMethod` gate never auto-retries it), `404`/`422`/other non-2xx → `APIError(3)` with the RFC 9457 detail surfaced, not-authenticated → the shared fail-safe; exit non-zero.

The `prp_` id is escaped as one path segment (`url.PathEscape`) but passed through unvalidated, so a malformed or unknown id reaches the API as a clean `404` (a real failure here — ADR-3). For `json`/`yaml` the command emits the raw `{data: Proposal}` bytes verbatim (018, via `output.RenderSuccess`); for human/`-o template` it renders the decoded `ProposalView` through `writeHuman` (019/035). Adds no new `Outcome`/`ExitCode`.

## Architecture Decisions

### ADR-1: `propose <prp-id>` as a new flagless leaf on the `proposal` group, sending a bodyless POST to the `/propose` sub-path

**Context**: The spec fixes the surface as `proposal propose <prp-id>` — continuing the verb grammar 056 ADR-1 forced for the verb-rich proposal noun (create / propose / withdraw / respond), where a bare `proposal <prp-id>` would collide with subcommand dispatch. The transition maps to `POST /proposals/{proposal_id}/propose` — keyed off a *proposal* id like `get`, but a **sub-resource action path** (`/{id}/propose`), not the collection path the reads/creation use. Unlike every prior write leaf it has **no editable inputs**: it advances a proposal whole, so it needs no field flags and **no request body** (`proposeProposal` defines no `requestBody`). As of the base, **no `proposal` group exists** — 055/056 are concurrent in parallel workspaces.

**Options considered**:
1. **New `propose <prp-id>` leaf on `newProposalCommand`, no flags, bodyless POST** — `ExactArgs(1)` over the `prp_` id, only the inherited persistent flags, `runProposalPropose` mirrors the sibling orchestration shape. Conforms to 056 ADR-1's verb-grammar group and the structural guard; the smallest possible surface.
2. **A separate top-level `proposal-propose` command** — rejected: 056 ADR-1 claimed `proposal` as the verb namespace; a parallel surface would fork the family the group exists to hold (the same rejection 045 ADR-1 / 044 ADR-2 recorded).

**Decision**: Option 1. Add `newProposalProposeCommand(seam)` and attach it in `newProposalCommand` beside `list`/`get` (and `create`); widen the group `Short` to name `propose`. The leaf declares no flags, so a stray `--status`/`--body` is a free cobra unknown-flag `UsageError(2)`. The request is built with `Method: http.MethodPost`, `Path: /proposals/{prp_id}/propose`, **no `Body`**, `ContentType` left `""` (so no `Content-Type` header — a bodyless POST, the discard `DELETE` shape, not the createTension body shape), and `out` a `*Document[Proposal]` to decode the `200`. The `prp_` id is escaped as one path segment and passed through unvalidated (no local `^prp_…$` regex), per the 045/056 pass-through rule.

**Consequences**: The `proposal` family gains its first transition verb with a zero-flag, zero-body surface. This is the **first bodyless POST that also decodes a response** — createTension is POST+body+decode, discard is bodyless-DELETE+no-decode; propose is bodyless-POST+decode, a new combination of landed transport (the free-string `Method`, the optional `ContentType` from 042 §283, and `Execute`'s `out` decode all already support it — no transport change). Silent conformance to the verb-grammar placement precedent (no new DECISIONS entry for the placement itself; ADR-2/ADR-3 carry the novelty). The sibling coordination is in Risks.

### ADR-2: Decode and render the server-returned `{data: Proposal}` through the shared singular `proposal` render path — decode, do not synthesize

**Context**: A successful `proposeProposal` returns **`200` with the advanced `Proposal`** — the full resource, now in `proposed_outside_meeting`, carrying the server-computed `response_deadline`, the proposer's auto-recorded implicit `no_objection` (reflected in `response_summary` / `received_response_count`), and updated `available_transitions`. This is the **opposite of discard's bodyless success** (045 ADR-3 / §339), which had nothing to echo and so synthesized a command-local `{data:{id,discarded}}`. Here the server's payload *is* the result, and it is the same `Proposal` shape `proposal get` decodes and renders.

**Options considered**:
1. **Decode `Document[Proposal]` and render through the existing singular `proposal` path** — `output.RenderSuccess` over the raw `{data: Proposal}` bytes for a machine format (faithful regardless of model field coverage), `writeHuman` over the decoded `ProposalView` for human/`-o template` — exactly as `proposal get` does. Reuses 056/055's model and singular render unchanged; the advanced proposal is surfaced with the same fidelity as a read.
2. **Synthesize a thin result (id + new status)**, the discard shape. Rejected: the server returned the whole advanced proposal — a richer, truthful payload — and the family already has the singular render for it; synthesizing would *discard server-confirmed data* (the deadline, the implicit response, the new transitions) the operator and downstream automation want, and fork the render path for no gain.

**Decision**: Option 1. `runProposalPropose` decodes the `200` into the sibling-owned `Document[Proposal]` and dispatches on the resolved render target exactly as `get` does — `RenderSuccess(machineFmt, raw)` for a built-in machine format (the raw `{data: Proposal}` bytes, so any field the model omits still appears under `-o json`), `writeHuman(…, ResourceProposal, …)` over the decoded `ProposalView` otherwise (buffer-then-write, so a render failure leaves stdout empty and maps to `RuntimeError(1)`). The command **adds no model and no render surface** — it is the first proposal write to be a pure consumer of both. It surfaces the proposal exactly as returned and **narrates none of the side effects** (notifications, the deadline computation, the implicit response) — those are visible only through the returned data (spec non-behavior).

**Consequences**: The advance result has full read-grade fidelity — `-o json/yaml` is the verbatim server proposal, `-o full` the same view a read renders. Contrasts the discard precedent at the type level: a write whose success **echoes a server resource** decodes-and-renders, where a write whose success is **bodyless** synthesizes (045) — the two now bracket the write-output design space. This consumer-only stance depends entirely on 056/055 having landed the model + singular render (Risks). The exact rendered fields are 056/055's interface contract; nothing here is interface-level new. Cross-spec relevant (Withdraw / Response Recording return `Proposal`s too and will reuse this decode-and-render path) → record in DECISIONS.md.

### ADR-3: Treat the transition as server-authorized — no client pre-check; 404 and 422 are real failures; the Premium 403 routes through the shared classifier with no plan-gate special-casing

**Context**: `proposeProposal` is allowed **only when `propose` is in the proposal's `available_transitions`**, and is **Premium-gated** (`403` when async proposals are not enabled). Its documented non-2xx responses are `401`, `403`, `404`, `422`. The spec's defining decisions: the command does **not** pre-read the proposal to check `available_transitions` (the reads surface that list — 056 — but invoking the transition is this command's job, and a pre-read adds a round-trip and a stale-snapshot risk); a `422` (transition not allowed — not a `draft`, or `propose` not offered) and a `404` (no such or invisible proposal) are **real failures**, *not* success — explicitly **unlike** discard, which folds its `404` into success (045 ADR-2 / §336) because a soft-delete has an idempotent end-state and an advance does not; and the Premium `403` gets **no special "not available on your plan" treatment** — distinguishing a plan-gate `403` from a permission `403` is the separate Plan-Limit Signalling capability, out of scope here.

**Options considered**:
1. **Pre-read the proposal, check `available_transitions` locally, only POST if `propose` is present** — rejected: forks the server's authority over the transition rule, adds a `GET` round-trip, and can act on a stale snapshot (the window between read and write); the server already enforces with a `422`. The spec makes the no-pre-check a non-behavior.
2. **Fold `404`/`422` into success (the discard idempotency shape)** — rejected: an advance has no idempotent re-run. Re-proposing a circulating proposal is a genuine `422` (`propose` no longer offered) the operator must see, and a `404` is a real missing proposal; treating either as success would hide exactly the failures the command exists to surface. Discard's `404`-as-success is grounded in a soft-delete's identical end-state — that grounding is absent here.
3. **Issue the bodyless POST and route every non-2xx through the shared classifier unchanged; add no plan-gate handling** — chosen. The command lets the server authorize the transition (a `422` if not allowed) and classifies `404`/`422`/other as `APIError(3)`, `401`/`403` as `PermissionError(4)`, `429` as `RateLimited(5)`, transport as `NetworkUnavailable(6)` — the landed `reportFailure` chain, no special cases.

**Decision**: Option 3. `runProposalPropose` sends the one `POST` and, on any error, calls `reportFailure` (the `me.go`/`clienterror.go` chain) with **no status interception** — the opposite of discard's `errors.As`-for-`404` divert. The Premium `403` is just a `PermissionError(4)` like any other refusal; this command adds no plan-aware branch (Plan-Limit Signalling, when it lands, refines the `403` signal centrally, the way 054 refined the `412` for all writes — not per-command here). No new `Outcome`/`ExitCode`.

**Consequences**: The command is a faithful surface over a server-authorized transition: the server is the single source of truth for whether `propose` is allowed, and every failure is surfaced loudly with its HTTP status and a next step. It establishes the **inverse of the discard idempotency precedent** — a write whose success has *no* idempotent re-run treats `404`/`422` as real failures — bracketing §336 (when a non-2xx *is* success) against this (when it is not). The Premium `403` deliberately stays generic, leaving the dedicated plan-gate signal to its own capability. A `429` on this `POST` is never auto-retried (017's `isSafeMethod` gate is GET/HEAD-only), so the advance cannot double-fire. Cross-spec relevant (the no-pre-check + real-failure stance is the template for Withdraw and Response Recording transitions) → record in DECISIONS.md.

## Cross-cutting Concerns

**Sibling coordination (055 Proposal Creation / 056 Proposal Reads)** — the only non-trivial cross-cutting concern. 057 consumes three artifacts a sibling owns: the `proposal` group (`newProposalCommand` + the `proposalSeam`), the `glassfrog.Proposal` model + `Document[Proposal]` decode, and the singular `proposal` render path (`ProposalView`/`ResourceProposal`/`proposal.{full,compact}`). Design contract: **first-to-land creates, follower reuses** (056's resolved relationship to 055). 057 is almost certainly a follower (056 is Analyzed, 055 in flight, 057 just Specified): it rebases onto the landed group, attaches its `propose` leaf, and reuses the model and singular render unchanged — it grows neither. If 057 somehow lands first, it creates the *minimal subset it needs* — `newProposalCommand` + the `proposalSeam`, the `Proposal` model with `Document[Proposal]`, and the **singular** render path only (it needs no plural `proposals` render and no `validateProposalStatus`, which are list-only) — and 055/056 then reuse/grow those. Structured output is faithful regardless of model field coverage (raw-bytes pass-through via `RenderSuccess`), bounding the blast radius to human render + cobra wiring. See Risks.

**Failure mapping (no new outcomes)**: every failure routes through the landed `reportFailure` → `refineClientError`/`classifyClientError` chain (`me.go`/`clienterror.go`): not-authenticated → the shared fail-safe (`UsageError(2)` NoCredentials / `RuntimeError(1)` CredentialError); transport → `NetworkUnavailable(6)`; `401`/`403` → `PermissionError(4)` (the Premium `403` included — ADR-3); `429` → `RateLimited(5)`; `404`/`422`/other non-2xx → `APIError(3)` with the RFC 9457 detail surfaced. **No status is intercepted** (ADR-3) — the inverse of discard. The command adds no interpretation and never prints the token.

**Non-idempotent retry (silent conformance to §133)**: `propose` builds the same `NewRetryExecutor` as the rest, but 017's `isSafeMethod` restricts auto-retry-on-`429` to `GET`/`HEAD` (`retry.go:65`), so a `POST` `429` surfaces once and is never silently re-sent — the advance cannot double-fire (which matters, since re-firing a succeeded advance would be a `422`, not a no-op).

**Output**: success renders through the same buffer-then-write path as `proposal get` — `output.RenderSuccess` over the raw `{data: Proposal}` for a built-in machine format, `writeHuman` over the decoded `ProposalView` for human/`-o template` — so a render failure leaves stdout empty and maps to `RuntimeError(1)`. No stderr advisory (unlike discard's `204`-vs-`404` note — there is a single success outcome here).

**Testing**: the seam injection keeps `runProposalPropose` pure over a fake transport. Unit tests drive every branch offline — `200` success (asserting the decoded/raw proposal renders and exit `0`), `422` transition-not-allowed failure, `404` not-found failure (asserting it is **not** swallowed as success — the explicit contrast to discard), the Premium `403` (asserting it routes through `PermissionError(4)` with no plan-gate message), `429`, transport failure, not-authenticated, and a bad `--output` (a fail-fast `UsageError(2)` with a transport tripwire confirming **no request**). A focused test pins that the `POST` carries **no body and no `Content-Type`**, and that the command issues **exactly one** request and **no prior `GET`** (the no-pre-check validation scenario). A godog BDD suite mirrors the driving scenarios (the per-command `*_bdd_test.go` convention).

## Implementation Strategy

**Single phase — the `proposal propose` command**, a pure consumer of sibling-owned machinery. Build `newProposalProposeCommand` + `runProposalPropose` in `internal/cli` (resolve `--output` → assemble → one bodyless `POST /proposals/{id}/propose` with `out == &Document[Proposal]` → on success render the decoded/raw proposal; on any error `reportFailure` with no status interception); attach the leaf in `newProposalCommand` and widen the group `Short`; reuse the landed `proposalSeam`, `resolveRenderTarget`, `writeHuman`, `output.RenderSuccess`, the singular `proposal` render path, `reportFailure`/`refineClientError`/`classifyClientError`, and `NewRetryExecutor`; add BDD + unit tests. There is **no transport phase** (bodyless POST needs no new field — `Method` is a free string, `ContentType` already optional, `Execute` already decodes `out`), **no `internal/glassfrog` change**, and **no `internal/render` change** — the model and singular render are 055/056's. The whole feature is PR-sized.

**Dependency**: this phase requires the `proposal` group, the `Proposal` model, and the singular `proposal` render path to exist — landed by 055 or 056 (first-to-land-creates). The follower path (rebase + attach + reuse) is the expected case; the leads-first path (create the minimal subset) is the fallback (Risks).

## Risks

- **Sibling concurrency — the `proposal` group/model/render may not have landed (medium likelihood, low–medium impact)**: 057 consumes `newProposalCommand`, `glassfrog.Proposal`, and the singular `proposal` render path, all owned by 055/056 in parallel workspaces; landing order is unknown. *Impact*: if 057 is implemented before either sibling lands, those artifacts are absent. *Mitigation*: the first-to-land-creates / follower-reuses contract (System Architecture, Cross-cutting) — 057 rebases onto the landed group and reuses unchanged (expected, since 056 is already Analyzed); if it leads, it creates only the minimal subset it needs (group + seam, model + `Document[Proposal]`, singular render — no plural render, no status validator). Structured output is faithful regardless of model coverage (raw-bytes pass-through), bounding any conflict to human render + cobra wiring. Mirrors the 042→043 and 055/056 sequences, which resolve cleanly by rebase.
- **`404`/`422`-as-failure mistaken for the discard idempotency shape (low likelihood, medium impact)**: discard (045 §336) folds its `404` into success, and an implementer reusing the discard leaf as a template could carry the `errors.As`-for-`404` divert across. *Impact*: a re-proposed or unknown proposal would wrongly report success. *Mitigation*: ADR-3 is explicit that propose intercepts **no** status — every non-2xx routes through `reportFailure` unchanged; a unit test pins that a `404` and a `422` both exit non-zero and surface the status (the inverse-of-discard assertion).
- **Pre-read creep (low likelihood, low impact)**: `available_transitions` is available from the reads (056), tempting a client-side "is `propose` allowed?" check before the POST. *Impact*: an extra round-trip, a stale-snapshot race, and a forked authority. *Mitigation*: ADR-3 / spec non-behavior — the command issues the POST and lets the server's `422` enforce; a validation scenario asserts exactly one request and no prior `GET`.
- **Premium `403` over-handling (low likelihood, low impact)**: the Premium gate makes a bespoke "not available on your plan" message tempting. *Impact*: forking the plan-gate signal that belongs to Plan-Limit Signalling, producing inconsistent `403` handling across the write path. *Mitigation*: ADR-3 — the `403` stays a generic `PermissionError(4)`; a test asserts no plan-specific branch. The dedicated signal lands centrally in its own capability (as 054 refined the `412` for all writes).

## What This Plan Does Not Cover

- **Protocol-level contract** — the exact flag/help/`Long` text for the `propose` leaf, the request-descriptor field shape, and the rendered-field selection are the **interface** skill's concern; the singular `proposal` render contract is 055/056's. The names used here (`proposal propose <prp-id>`) are the spec-confirmed surface; treat them as the working contract, pinned at the interface stage.
- **Executable scenarios** — Gherkin for the driving scenarios is the **scenarios** skill's concern; the Driving Scenarios in spec.md are the source.
- **Task decomposition** — PR-sized units within the single phase are the **tasks** skill's concern.
- **The `Proposal` model, `Document[Proposal]` decode, the `proposal` group, and the singular `proposal` render path** — owned by Proposal Reads (056) / Proposal Creation (055); 057 reuses them (first-to-land-creates).
- **Plan-Limit Signalling** — distinguishing the Premium-gate `403` from a permission `403` is its own capability; here the `403` routes through the shared classifier (ADR-3). Out of scope.
- **Withdraw, Response Recording, and the rest of the write flow** — `proposal withdraw` / `proposal responses` are deferred to their own specs (spec non-behaviors); this plan advances only.
- **Optimistic concurrency (`If-Match`)** — `propose` is a transition with no `If-Match` parameter; Guarded Writes (053) applies to field edits, and its `Request.IfMatch` field stays unused here (053 §364). Out of scope per the spec non-behavior.
