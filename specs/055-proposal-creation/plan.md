## System Architecture

Proposal Creation is the CLI's **second write** and the anchor of the governance write path. Architecturally it is the Tension Capture (042) shape — resolve output format, validate input fail-fast, assemble the connection, build the retrying executor, send exactly one `POST` carrying a JSON body, then render the created resource or classify the failure — with one genuinely new ingredient: the request body's `changes` array comes from a **caller-supplied JSON source** (inline string / file / piped `stdin`) that the command resolves, reads, and validates against a minimal floor before sending it through **verbatim**. It rides the proven chain end-to-end (the `ContentType` write-body seam already exists from 042; no transport change is needed) and reuses the landed bounded-stdin reader.

**Concurrent sibling — Proposal Reads (056).** 055 and 056 were specified in parallel and both introduce the `proposal` command group (`newProposalCommand`), the `glassfrog.Proposal` response model (+ `ResponseSummary`), and the singular `proposal` render path. Neither is implemented yet (both are pre-implementation as of this plan). The design contract — mirroring 056's plan and the 042→043 sequence — is **first-to-land creates, follower reuses/grows**: as cut from current `main` (no proposal code present) 055 creates all three; **if 056 merges first**, 055 rebases and (a) attaches its `create` leaf to the existing group, (b) reuses 056's `Proposal`/`ResponseSummary` response model, and (c) reuses 056's singular `proposal` render (which is the richer one — it shows changes by type, the response summary, and available transitions — so 055's thinner created-proposal view is simply unneeded). 056 additionally owns the plural `proposals` render, the `list`/`get` leaves, and `validateProposalStatus` — none of which 055 touches. What 055 owns regardless of order is the **write request-input** type (`{proposal:{tension_id, changes}}`), which 056 never needs. See Cross-cutting Concerns and Risks.

**Components**:

- **`internal/cli/proposal.go`** (new) — a non-runnable `proposal` group command parenting a `create` leaf (`glassfrog proposal create <tension-id>`), registered through `Register` (001), mirroring the `tension` / `tension create` group/leaf pattern (042 ADR-2). The leaf carries `--changes`, inherits the persistent `--base-url`/`--output`, takes exactly one required positional (`ExactArgs(1)`, the 042 shape), and delegates to a pure `runProposalCreate(cfg)` over the 042 `tensionSeam` shape (`assemble` / `newClient` / `sleep` / `resolveSelection` / `readTemplateSource`) **plus one new seam member** — `readChangesSource(value string) ([]byte, error)` — so every branch (source read, parse, validation, send, render) runs offline against fakes. `runProposalCreate` resolves the format, reads+parses+validates the change set (ADR-3), builds the JSON body, sends one `Execute` to `POST /proposals`, and renders the created proposal.
- **`internal/cli` change-source resolution** (new, in `proposal.go`) — a pure `resolveChangesSource(value string, stat …, readFile …, isTTY bool, stdin io.Reader) ([]byte, error)` classifying the `--changes` value: the reserved keyword `stdin` → the bounded stdin reader (reusing `readBoundedStdinN` with a changes cap + the TTY/empty guard, 006/035 shape); a value that **stats to an existing regular file** → `os.ReadFile`; anything else → the value's own bytes as **inline JSON** (ADR-2). The `productionSeam.readChangesSource` binds the real `os.Stat`/`os.ReadFile`/`os.Stdin`.
- **`internal/glassfrog/proposal.go`** (shared with 056 — created by whichever lands first) — the `Proposal` response model (matching the v5 `Proposal` schema: `id` `prp_`, `type`, `status`, `tension_id`, `circle_id`, `proposer_id`, `changes`, `response_summary`, `available_transitions`, the response-count/timestamp fields, snake_case tags, forward-compatible decoding) + `ResponseSummary`, with the response `changes` decoded as `[]ProposalChange` (056 ADR-2: `ID`/`Type` + a free-form `map[string]any` remainder, the `actions.go` precedent). Models live here per 011 ADR-1 (grow/add in `glassfrog`, never command-local). 055 **additionally** adds the write request-input type encoding `{proposal: {tension_id, changes}}`, where the request `changes` is `[]json.RawMessage` so each supplied change is sent **byte-for-byte** above the `type` floor (ADR-3/ADR-4) — distinct from the response decode shape, and 056 never needs it. The token is never a field (CONSTITUTION II).
- **`internal/render`** (singular `proposal` key — shared with 056, created by whichever lands first) — the singular `proposal` view renders the created proposal on the human path (surfacing the load-bearing `prp_` id and `draft` status); the machine path reuses `output.RenderSuccess` over the raw `{data}` bytes (silent conformance to the 018/020 single-read pattern). If 055 lands first it adds a thin created-proposal view (id, status, anchor, change count, transitions); if 056 lands first, 055 reuses 056's richer singular `proposal` view (changes by type, response summary, transitions) unchanged. Exact view content is interface-level.

**Data flow**: `proposal create <tension-id> --changes <src>` → resolve format (020/035) → `readChangesSource` (stdin/file/inline) → parse JSON + validate: array, non-empty, every element an object with a non-empty `type` (fail-fast, **no request**) → assemble (009) → `NewClient` (008/007) → `NewRetryExecutor` (017) → marshal `{proposal:{tension_id, changes}}` → one `Execute` `POST /proposals` with `Content-Type: application/json` (010/042, `X-Auth-Token` via 007's transport) → on 201 decode `Document[Proposal]`; machine renders raw `{data}` (018), human renders the proposal view (019) → success (0). On any failure, `reportFailure` + `classifyClientError`/`refineClientError` (015/017) map status to the existing outcomes; no new `Outcome`/`ExitCode`.

## Architecture Decisions

### ADR-1: `proposal create <tension-id>` as a group + leaf, reserving the `proposal` namespace

**Context**: The spec fixes the surface as `glassfrog proposal create <tension-id>`, deliberately leaving room for the rest of the write flow (`proposal list/get/propose/withdraw/respond`) as future siblings. The registration guard (001) requires a command be *either* a leaf (with an action) *or* a group (with ≥1 child), never both. Tension Capture (042 ADR-2) already settled this exact shape for the first write, recorded as cross-spec precedent.

**Options considered**:
1. **Non-runnable `proposal` group + `create` leaf** — `proposal` parents `create`; `proposal` alone prints help. Matches `tension`/`tension create` (042) and the registration guard's group rule; reserves the `proposal` namespace for the write-flow siblings without re-litigating the surface.
2. **Flat `proposal-create <tension-id>` leaf** — a single hyphenated command, no group. Forecloses a clean `proposal <verb>` family and reads awkwardly beside the noun-led commands.

**Decision**: Option 1 — a non-runnable `proposal` group parenting a `create` leaf, both assembled and attached through `Register` (the group is built with its child before being registered under root, so the guard's ">=1 child" rule holds at attach time). This is **silent conformance** to the 042 namespace precedent, extended to the proposal noun. The `--changes` flag lives on `create`, so a future `proposal get`/`propose` adds its own leaf with its own flags — passing `--changes` to a read is a cobra unknown-flag usage error for free.

**Consequences**: `proposal` with no subcommand prints help. The write-flow siblings (advance/respond/withdraw) and the reads add their own leaves under the reserved namespace. No `tension`-style coupling and no runnable parent. **Concurrent-sibling coordination (056)**: 056 Proposal Reads also creates this group (for its `list`/`get` leaves). First-to-land creates `newProposalCommand`; the follower attaches its leaf(s) to the existing group rather than creating a second one (043's relationship to 042's `newTensionCommand`). Cross-spec relevant (sets the `proposal` namespace the whole write-flow conforms to) → record in DECISIONS.md.

### ADR-2: Resolve `--changes` from a reserved `stdin` keyword, an existing file, or inline JSON — behind a filesystem + stdin seam

**Context**: `--changes` carries a JSON array from one of three sources (spec clarification): the reserved keyword `stdin`, a file, or an inline JSON string. Distinguishing a file path from an inline JSON value cannot be done purely — it needs a filesystem check. The codebase already resolves a *template* source (035) with a reserved `stdin` keyword and a bounded stdin reader, but a template's non-`stdin` value is *always* a file (templates have no inline form), so 035's classifier does no existence check and has no inline branch.

**Options considered**:
1. **Reuse 035's `TemplateRef` classifier verbatim** — treat any non-`stdin` value as a file path. Rejected: it has no inline-JSON branch, so the spec's primary case (a small inline array on argv) would be read as a (missing) file path and fail.
2. **A dedicated change-source resolver: `stdin` keyword → bounded stdin; value that stats to an existing regular file → read file; else → inline JSON bytes.** Reuses 035's reserved-`stdin` idiom and the landed `readBoundedStdinN` bounded reader (006), adds the existence check + inline fallback the change set needs. Kept pure (`stat`/`readFile`/`isTTY`/`stdin` injected) so every branch is offline-testable, with the real binders in `productionSeam.readChangesSource`.
3. **Separate `--changes` (inline) and `--changes-file` flags** — rejected during clarification in favour of one flag resolved by convention.

**Decision**: Option 2. `resolveChangesSource` mirrors 035's reserved-keyword-wins shape and reuses `readBoundedStdinN` (with a changes byte cap and the same TTY/empty fail-fast: piped-stdin-required, empty-pipe rejected), and **announces its divergence** from 035: it adds an `os.Stat`-based existing-regular-file check and an inline-JSON fallback, because the change set — unlike a template — has a first-class inline form. A file literally named `stdin` is reachable as `./stdin` (035's reserved-name escape). Reading lives behind the seam (035 ADR-4: the resolver is pure over injected `stat`/`readFile`/`stdin`); a stat/read/empty-pipe failure is a `UsageError(2)` naming the source, raised before any request.

**Consequences**: The CLI gains its first JSON-body-from-source input, set up so future proposal/operational writes that take a free-form body follow the same `stdin`/file/inline resolution. The `lstat`-style regular-file guard avoids reading a directory as a change set. Cross-spec relevant → record in DECISIONS.md.

### ADR-3: Validate the change set fail-fast against a `type` floor; pass it through verbatim above the floor

**Context**: `--changes` carries a free-form governance-command array — `ProposalChange` is `type` plus open, command-specific keys, with **no per-type schema** in the spec. The spec's clarified floor: valid JSON, a non-empty array, and every element an object with a non-empty `type` (the one key the schema marks required); beyond that, the array is sent untouched and the server validates `type` values and command keys. Tension Update (044) set the write-path rule "fork a typed input when client contracts diverge" — but that is for *typed* bodies; the change set is deliberately *untyped* here (typed per-change builders are the deferred *Unguided Change Construction* problem).

**Options considered**:
1. **Floor-only validation over a verbatim `[]json.RawMessage`** — parse the source bytes as a JSON array; reject (`UsageError(2)`, no request) if it is not valid JSON, not an array, empty, or contains an element that is not an object or lacks a non-empty `type`. Keep each element as `json.RawMessage` so it marshals into the request body **byte-for-byte**, preserving every command-specific key untouched and unread.
2. **Typed per-change models** (a `CreateRole` struct, an `UpdateAccountability` struct, …) validated client-side. Rejected: this *is* the deferred Unguided Change Construction capability; the spec non-behavior forbids it here, and there is no per-type schema to model against.
3. **Zero client validation** (send any non-empty array verbatim). Rejected at clarification: a typeless element is knowable-bad locally (the schema requires `type`), so the §113 "validate what's knowable client-side" rule applies — a local floor gives a clearer error than a server `422`.

**Decision**: Option 1. The validation is pure and pre-assembly (the 042/044 fail-fast discipline, a transport tripwire pinning "no request issued" on every rejection): resolve `--output` first, then read+parse the source, then apply the floor. `--changes` absent → `UsageError(2)` naming `--changes` required. The `type` floor reads only each element's `type` (decoding each `json.RawMessage` into a minimal `{type string}` probe); all other keys ride through verbatim. No new `Outcome`/`ExitCode`. This is the *anti*-044 case made explicit: where 044 forked a typed input because contracts diverged, 055 keeps an untyped raw pass-through because the API itself is schema-free here — the floor is the only knowable-local check.

**Consequences**: Malformed-but-typed changes still reach the server and surface as a clean `422` (server-owned validation). The verbatim `[]json.RawMessage` guarantees the CLI neither reshapes nor drops command keys. The floor is the seam where the future typed builders (Unguided Change Construction) would later attach. Cross-spec relevant (the free-form-body pass-through-above-a-floor rule) → record in DECISIONS.md.

### ADR-4: Share the `Proposal` response model + singular render with 056 (first-to-land creates); add only the write request-input

**Context**: The 201 returns `{data: Proposal}` — a rich resource (status, anchor tension, aggregate `response_summary`, `available_transitions`, response counts, timestamps). The command must render it on both the machine and human paths. 011 ADR-1 governs response models: grow/add in `internal/glassfrog`, decode through the generic `Document[T]`, render machine as raw `{data}` and human through a per-resource view. The wrinkle is the **concurrent sibling 056 Proposal Reads**, which decodes the *same* `Proposal` schema and was specified in parallel — so the model and singular render are shared, not 055's alone.

**Options considered**:
1. **Share the `Proposal` model + singular `proposal` render with 056 (first-to-land creates, follower reuses/grows); 055 adds only the write request-input type.** Conforms to 011 ADR-1, the §143/§254 generic-envelope rule, and the 042→043 shared-symbol precedent. The response `changes` decode as `[]ProposalChange` (056 ADR-2: `ID`/`Type` + a free-form `map[string]any` remainder), reused as-is.
2. **A 055-private `Proposal` model + a second singular render.** Rejected: 056 decodes the identical schema; two `Proposal` types and two singular `proposal` render keys would duplicate and collide (the exact thing the first-to-land/follower contract avoids).
3. **Render the raw JSON only** (no human view). Rejected: every landed read/write offers a human view; a write that returns only raw JSON would fork the 019/020 contract.

**Decision**: Option 1. The `Proposal`/`ResponseSummary` response model and the singular `proposal` render key are **shared with 056** under first-to-land-creates / follower-reuses-or-grows. If 056 lands first, 055 reuses its `Proposal` (response `changes` = `[]ProposalChange`) and its richer singular `proposal` view (changes by type, response summary, available transitions) **unchanged** — the created proposal renders through it, surfacing the load-bearing `prp_` id and `draft` status. If 055 lands first, it adds a thinner created-proposal view (id, status, anchor, change count, transitions) that 056 then grows. Either way the response decodes forward-compatibly. **055's own net-new contribution** is the write request-input type `{proposal:{tension_id, changes []json.RawMessage}}` (verbatim send, ADR-3) — 056 has no write and never adds it.

**Consequences**: No duplicate `Proposal` type and no second singular render key. `Document[Proposal]` needs no new envelope. Cross-spec relevant (the shared `Proposal` model + render, and 055's exclusive write request-input) → record in DECISIONS.md.

## Cross-cutting Concerns

**No transport change (silent conformance to 042 ADR-1)**: the write body's `Content-Type: application/json` rides the landed `apiclient.Request.ContentType` field; no `apiclient` change is needed. A create has **no prior `ETag`**, so no `If-Match` is sent — the 052/053/054 optimistic-concurrency mechanism is deliberately untouched (spec non-behavior; a create cannot clobber).

**Premium gate is server-surfaced, never pre-checked**: the command always issues the request; a `403` (async proposals disabled) classifies through the landed 015 path as `PermissionError(4)` with the RFC 9457 detail surfaced. Recognizing the feature-gate and signalling a plan limit distinctly are Feature-Gate Recognition (060) / Plan-Limit Signal (061) — future specs; this command adds no client-side Premium check (spec non-behavior).

**Non-idempotent retry (silent conformance to §133)**: `create` uses the same `NewRetryExecutor` as the reads, but 017's `isSafeMethod` restricts auto-retry-on-429 to `GET`/`HEAD` — a `POST` surfaces the `429` on first occurrence and is **never silently re-sent**, so creation cannot double-submit a proposal on a rate-limit retry.

**Failure mapping (no new outcomes)**: every failure routes through the landed `reportFailure` → `refineClientError`/`classifyClientError` chain. Not-authenticated → the shared fail-safe; transport → network-unavailable; non-2xx via 015's `ExtractProblem` — `403` (Premium) / `401` → `PermissionError(4)`, `404` (unknown anchor tension) and `422` (rejected change/field) → `APIError(3)` with the detail surfaced, `429` → `RateLimited(5)`. The change-source fail-fast errors (missing `--changes`, unparseable/non-array/empty/typeless, unreadable file, empty pipe) are `UsageError(2)`, raised before assembly. The command adds no interpretation and never prints the token.

**Output**: the 201 `{data: Proposal}` decodes into the generic `Document[Proposal]` (no per-resource envelope — §143/§254). Machine formats emit the raw `{data}` via `output.RenderSuccess`; the human path renders the shared singular `proposal` view surfacing the `prp_` id and `draft` status. Buffer-then-write so a render failure leaves stdout empty and maps to `RuntimeError(1)`.

**Concurrent-sibling coordination (056 Proposal Reads)** — the one non-trivial cross-cutting concern. 055 and 056 share the `proposal` group (`newProposalCommand`), the `glassfrog.Proposal`/`ResponseSummary` response model, and the singular `proposal` render key; both were specified in parallel and neither is implemented. Design contract: **first-to-land creates, follower reuses/grows** (043's resolved relationship to 042). As cut from current `main` (no proposal code present), 055 creates all three. **If 056 merges first**, 055 rebases and (a) attaches its `create` leaf to the existing group, (b) reuses 056's `Proposal`/`ResponseSummary` (response `changes` = `[]ProposalChange`), and (c) reuses 056's richer singular `proposal` view unchanged. Structured `json`/`yaml` output is faithful regardless of model field coverage (`output.RenderSuccess` passes the raw server bytes through), bounding any conflict to human render + cobra wiring. 055's exclusive surface is the **write request-input** (`{proposal:{tension_id, changes []json.RawMessage}}`), `resolveChangesSource`, and the `type` floor — none shared with 056. See Risks.

**Testing**: seam injection keeps `runProposalCreate` and `resolveChangesSource` pure over fakes — unit tests drive happy/usage/failure branches offline (inline / file / stdin sources; missing/empty/non-array/typeless change sets; missing positional); a transport tripwire pins "no request issued" for every fail-fast rejection; the verbatim pass-through is asserted by comparing the marshalled `proposal.changes` bytes to the supplied array; a godog BDD suite mirrors the driving scenarios (the per-command `*_bdd_test.go` convention). The stdin arm is tested through the injected reader (no real pipe), reusing the 035/006 bounded-reader test shape.

## Implementation Strategy

**Phase 1 — Request-input, change-source resolution, and the `type` floor**: add the write request-input type `{proposal:{tension_id, changes []json.RawMessage}}` (055's exclusive surface); reuse-or-create the shared `glassfrog.Proposal`/`ResponseSummary` response model per the 056 coordination (create it only if 056 hasn't landed it); add the pure `resolveChangesSource` (reserved `stdin` / existing-file / inline, reusing `readBoundedStdinN` with a changes cap) and the `type`-floor validator (valid JSON, non-empty array, each element an object with a non-empty `type`). All pure/offline — unit-tested over injected sources and a tripwire. (PR-sized.)

**Phase 2 — The `proposal create` command**: build the `create` leaf in `proposal.go` (its write seam = the `tensionSeam` shape + `readChangesSource`, `runProposalCreate`: resolve format → read/parse/validate changes → assemble → marshal `{proposal:{…}}` → one `Execute` `POST /proposals` with `application/json` → render/classify); attach the leaf to the `proposal` group (creating `newProposalCommand` only if 056 hasn't); render the created proposal through the shared singular `proposal` view (reuse 056's if present, else add a thin one); add the `productionSeam.readChangesSource` binder; BDD + unit tests. Depends on Phase 1.

## Risks

- **Inline-vs-file misclassification** — a `--changes` value meant as inline JSON that happens to match an existing file path would be read as a file. Likelihood very low (inline JSON begins with `[`, never a plausible bare path) and impact low (the file's JSON is parsed and validated identically). Mitigation: the existence check uses a regular-file guard (a directory is not a source); documented in the spec assumption.
- **Verbatim pass-through ships a bad-but-typed change** — a change with a valid `type` but wrong command keys reaches the server. By design: the server owns per-change validation and answers `422`, surfaced cleanly through 015. No mitigation needed; it is the deferred-typed-builders boundary.
- **Premium `403` reads as a generic permission error** — the operator sees a permission outcome, not "enable async proposals / upgrade your plan". Accepted: distinct plan-limit signalling is Feature-Gate Recognition (060) / Plan-Limit Signal (061); the detail string still surfaces the server's explanation.
- **Double-submit on retry** — likelihood very low (already mitigated), impact high (duplicate governance proposals). Mitigation: §133's `isSafeMethod` gate; a test asserting a `POST` 429 is surfaced, not retried.
- **056 Proposal Reads concurrency (medium likelihood, low–medium impact)** — 055 and 056 both introduce the `proposal` group, `glassfrog.Proposal`/`ResponseSummary`, and the singular `proposal` render key; landing order is unknown (parallel workspaces). *Impact*: a merge conflict on `newProposalCommand`, `proposal.go`, and the singular render if both create them. *Mitigation*: the first-to-land-creates / follower-reuses-or-grows contract (ADR-1, ADR-4, Cross-cutting) — the follower rebases, attaches its leaf, and reuses (or grows) the model/render. Structured output is faithful regardless of model coverage (raw-bytes pass-through), bounding the conflict to human render + cobra wiring. Mirrors the 042→043 sequence, which resolved cleanly by rebase. 055's write request-input, `resolveChangesSource`, and `type` floor are exclusive to 055 and conflict-free.

## What This Plan Does Not Cover

- **Protocol-level contract** — exact flag spellings, help text, the `--changes` source-resolution error wording, the request/response field mapping, and the render view layout are the **interface** skill's concern.
- **Executable scenarios** — Gherkin for the driving scenarios is the **scenarios** skill's concern.
- **Task decomposition** — PR-sized units within the two phases are the **tasks** skill's concern.
- **The rest of the proposal write-flow and the reads** — advance-to-circulation, respond, and withdraw are deferred to their own specs; `list`/`get` are the concurrently-specified Proposal Reads (056), which shares the `proposal` group/model/render per the coordination contract (Cross-cutting). This plan designs only `create`.
- **Optimistic concurrency (`If-Match`)** — a create has no prior `ETag`; the 052/053/054 mechanism is untouched (spec non-behavior).
- **Premium feature-gate recognition and plan-limit signalling** — Feature-Gate Recognition (060) / Plan-Limit Signal (061); this command only surfaces the server's `403` through the shared permission outcome.
- **Typed per-change builders** — recognizing each change `type` and validating its keys is the deferred *Unguided Change Construction* problem; this command keeps the change set a verbatim pass-through above the `type` floor (ADR-3).
