## System Architecture

Withdraw Proposal is the **`withdraw` transition leaf of the `proposal` family** — and, unlike Advance to Circulation (057), it lands into a codebase where **every piece of machinery it needs already exists on `main`**. 055 (Proposal Creation), 056 (Proposal Reads), 057 (Advance to Circulation) and 058 (Response Recording) have all merged, so the `proposal` group (`newProposalCommand`/`proposalSeam`), the `glassfrog.Proposal` model + `Document[Proposal]` decode, and the singular `proposal` render path (`ProposalView`/`ResourceProposal`/`proposal.{full,compact}`) are landed and proven. More: 057's `proposal propose` leaf (`internal/cli/proposal_propose.go`) is the **near-exact structural twin** of this command — a flagless, bodyless `POST` to a transition sub-path that decodes and renders the returned `Proposal`. 059 is therefore a *pure follower of a single landed sibling*: it is `propose` with `/propose` → `/withdraw` and `draft → circulating` → `circulating → draft`. There is **no sibling-coordination race** (the defining risk of 057) and **no first-to-land-creates contract** — the group, model, render, and leaf template are all simply there to reuse.

It introduces **no new transport, model, render, error, or outcome machinery**. It sends one **bodyless** `POST /proposals/{proposal_id}/withdraw` with `out == &Document[Proposal]`, decodes the returned `{data: Proposal}` (now back in `draft`, with `proposed_at`/`response_deadline` cleared and prior responses deleted server-side), and renders it through the same flow `proposal get`/`proposal propose` use. It adds **no `internal/glassfrog` change** (the `Proposal` model is 055/056's) and **no `internal/render` change** (the singular `proposal` view/templates are 055/056's). Its only net-new surface is one cobra leaf (`newProposalWithdrawCommand`) and its pure `run` function (`runProposalWithdraw`), built by mirroring `proposal_propose.go`.

Three properties of `withdrawProposal` shape the flow, and all three are **already-landed precedents** from 057 (silent conformance — see ADR-1). First, the request is a **bodyless POST to a sub-resource path** — `Method: http.MethodPost`, no `Body`, `ContentType` left `""`, `out` a `*Document[Proposal]`. Second, the success carries a **real payload** — the withdrawn `Proposal`, now `draft` — so the command **decodes and renders** the server's proposal rather than synthesizing a result (057 §393). Third, the transition is **server-authorized** — allowed only when `withdraw` is in `available_transitions`, enforced with a `422` — so the command issues the `POST` and lets the server decide, and treats `422` (transition not allowed — already `draft`, or `withdraw` not offered) and `404` (no such proposal) as **real failures**, never folding them into success the way discard (045) folds its `404` (057 §396).

The one property that is **genuinely new to 059** is that the transition is **destructive**: the server deletes all existing `proposal_responses` and clears `proposed_at`/`response_deadline`. This is the inverse of `propose`, which *sets* those fields and records an implicit response. That destructiveness drives the single 059-specific decision (ADR-2): the command surfaces the returned draft proposal faithfully, **narrates none of the deletion**, and adds **no confirmation/`--force` guard** — the non-interactive, agent-driven contract holds, and an operator-layer destructive-write confirmation is the separate Write-Safety Guardrail capability, not this command's job.

**Components**:

- **`internal/cli/proposal_withdraw.go`** (new) — a `withdraw <prp-id>` leaf attached to the `proposal` group (`newProposalCommand`), beside the landed `create`/`propose`/`respond`/`list`/`get`. `cobra.ExactArgs(1)` over the `prp_` id; **no flags** beyond the inherited persistent `--base-url`/`--output` (a transition has nothing to edit), so a stray flag is cobra's own unknown-flag `UsageError(2)`. It delegates to a pure `runProposalWithdraw(cfg)` over the landed **`proposalSeam`**, so every branch (success, transport, non-2xx, not-authenticated, bad-`--output`) runs offline against a fake transport. The group `Short` widens to name `withdraw`.
- **No `internal/glassfrog` change** — the `200` decodes into the landed `Document[Proposal]`; no model field is added.
- **No `internal/render` change** — the withdrawn proposal renders through the landed singular `proposal` path (`ProposalView` + `ResourceProposal` + `proposal.{full,compact}`) for human output, and `output.RenderSuccess` over the raw `{data: Proposal}` bytes for `json`/`yaml`.

**Data flow** (identical to `propose`, with `/withdraw` for `/propose`): `withdraw <prp-id>` → resolve render target (020/035); a bad `--output` is a fail-fast `UsageError(2)`, no request → `assemble` (009) → `newClient` (008/007) → `NewRetryExecutor` (017) → one `Execute` `POST /proposals/{prp_id}/withdraw`, **no body, no `Content-Type`**, `out == &Document[Proposal]` (010) → branch on the outcome:
- `err == nil` (a `200`): success — render the decoded/raw proposal (now `draft`) and exit `Success(0)`.
- any error: `reportFailure` → `refineClientError`/`classifyClientError` (015/017) maps transport → `NetworkUnavailable(6)`, `401`/`403` → `PermissionError(4)` (the Premium `403` included — no plan-gate special-casing), `429` → `RateLimited(5)` (a `POST`, so 017's `isSafeMethod` gate never auto-retries it), `404`/`422`/other non-2xx → `APIError(3)` with the RFC 9457 detail surfaced, not-authenticated → the shared fail-safe; exit non-zero.

The `prp_` id is escaped as one path segment (`url.PathEscape`) but passed through unvalidated, so a malformed or unknown id reaches the API as a clean `404` (a real failure here). Adds no new `Outcome`/`ExitCode`.

## Architecture Decisions

### ADR-1: Build `withdraw <prp-id>` as the structural twin of the landed `propose` leaf — flagless bodyless POST to the `/withdraw` sub-path, decode-and-render the returned `Proposal`, server-authorized (no pre-check; `404`/`422` real failures; generic Premium `403`)

**Context**: The spec fixes the surface as `proposal withdraw <prp-id>` — the mirror of `proposal propose <prp-id>` (057), continuing the verb grammar 056 ADR-1 forced and 055 §374 reserved (`list/get/propose/withdraw/respond`). The transition maps to `POST /proposals/{proposal_id}/withdraw` — a sub-resource action path keyed off a *proposal* id, with **no editable inputs** and **no request body** (`withdrawProposal` defines no `requestBody`). A successful withdraw returns **`200` with the withdrawn `Proposal`** (now `draft`). The transition is **server-authorized** (allowed only when `withdraw` is in `available_transitions`, enforced with `422`) and **Premium-gated** (`403` when async proposals are disabled); documented non-2xx: `401`/`403`/`404`/`422`. Every one of these properties was decided for `propose` and is now **landed precedent**: §392/§393 (decode-and-render the returned `Proposal`, do not synthesize) and §395/§396 (server-authorized — no client pre-check; `404`/`422` real failures, the inverse of discard's `404`-as-success; generic Premium `403`), both of which explicitly name **Withdraw** as the follower.

**Options considered**:
1. **Mirror the landed `propose` leaf onto the `/withdraw` path** — add `newProposalWithdrawCommand(seam)` + `runProposalWithdraw(cfg)` by copying `proposal_propose.go`'s structure, changing only the path segment (`/withdraw`), the help text (withdraw semantics, `draft` result), and the test fixtures. Silent conformance to the §393/§396 precedents; the smallest, most consistent surface; zero new machinery.
2. **A bespoke withdraw flow** (e.g. a pre-read of `available_transitions`, or a synthesized thin result, or `404`-as-success like discard) — rejected: each forks a precedent §396 settled deliberately. A pre-read forks the server's authority and risks a stale snapshot; a synthesized result discards the server-confirmed draft proposal (the cleared deadline, the updated transitions) the operator/automation want; `404`/`422`-as-success would hide the real failures a withdraw (which has no idempotent re-run — re-withdrawing a `draft` is a genuine `422`) must surface.

**Decision**: Option 1. Add `newProposalWithdrawCommand(seam)` and attach it in `newProposalCommand` beside the five landed leaves; widen the group `Short` to name `withdraw`. The leaf declares no flags, so a stray `--status`/`--changes`/`--body` is a free cobra unknown-flag `UsageError(2)`. The request is built with `Method: http.MethodPost`, `Path: /proposals/{prp_id}/withdraw`, **no `Body`**, `ContentType` left `""`, and `out` a `*Document[Proposal]` to decode the `200`. On success, render the decoded/raw proposal exactly as `propose`/`get` do (`output.RenderSuccess` over raw bytes for a machine format, `writeHuman` over `ProposalView` otherwise, buffer-then-write). On **any** error, route to `reportFailure` with **no status interception** — `404` and `422` are real failures; the Premium `403` is a generic `PermissionError(4)`. The `prp_` id is escaped one path segment and passed through unvalidated. No prior `GET`, no `If-Match`. No new `Outcome`/`ExitCode`/model/render key.

**Consequences**: The `proposal` family gains its second transition verb as a faithful twin of the first — maximal consistency, minimal surface, and behavior already proven by 057's tests. This is **silent conformance** to the §393/§396 precedents (which named Withdraw as the follower), so it sets no new cross-spec precedent of its own beyond confirming the pattern generalizes; the only DECISIONS-worthy novelty is ADR-2. The `429` is never auto-retried (017's `isSafeMethod` is GET/HEAD-only), so a withdraw cannot double-fire. Because all machinery is landed, the build is a single small file plus one registration line — no transport, model, or render change.

### ADR-2: Treat the withdraw's destructive side effects (deleted responses, cleared timestamps) as server-owned and faithfully surfaced — narrate nothing, add no confirmation/`--force` guard

**Context**: `withdrawProposal` is **destructive in a way `propose` is not**: the server documents that it *deletes all existing `proposal_responses`* (responders must re-respond if the proposal is later re-proposed) and *clears `proposed_at` and `response_deadline`*. The returned `200` proposal reflects this — back in `draft`, deadline gone, responses cleared. This is the single behavioral property 059 does not inherit from 057 (which *adds* a deadline and an implicit response). The spec settles it as a non-behavior: the command must not interpret, re-describe, warn about, or act on the deletion, and must not prompt for confirmation or require `--force`/`--yes`.

**Options considered**:
1. **Surface the returned draft proposal faithfully; narrate none of the side effects; add no confirmation guard** — the CLI is a faithful surface over the API (PROJECT/VISION Exclusion 1) and is built for non-interactive, agent-driven use. The deletion is visible only through the returned data (the now-empty `response_summary`, the cleared `response_deadline`). Conforms to 057 §393's "narrate none of the side effects" and to the no-confirmation stance every prior write took.
2. **Add a confirmation prompt or a required `--force`/`--yes` flag before withdrawing** — rejected: an interactive guard breaks the non-interactive contract the CLI is built around (an agent driving the CLI cannot answer a prompt), and a `--force` flag would be the first write to gate itself, forking the uniform write surface. Operator-layer confirmation for destructive writes is the separate **Write-Safety Guardrail** capability (named in PROJECT's "Agent operating surface"), which will add gating *across* the write path centrally — not per-command here.
3. **Emit a stderr advisory naming the deleted responses** (the 045 discard `204`-vs-`404` advisory shape) — rejected: discard's advisory disambiguated two indistinguishable success outcomes (`204` vs `404`); here there is a single success outcome and the deletion is already legible in the returned proposal (`response_summary` zeroed, deadline cleared). A bespoke advisory would narrate a server-owned side effect the spec says to leave to the data.

**Decision**: Option 1. `runProposalWithdraw` renders the returned `draft` proposal through the shared singular `proposal` path and adds **no** side-effect narration, **no** stderr advisory, and **no** confirmation/`--force`/`--yes` flag. The destructiveness is real but server-owned; the CLI surfaces the consequence (a `draft` proposal with no responses and no deadline) exactly as the API returns it.

**Consequences**: Withdraw stays a uniform, non-interactive write consistent with every sibling — an agent can withdraw and immediately re-read the now-`draft` proposal without handling a prompt. The deliberate cost — a mistaken withdraw silently discards responses — is accepted here and explicitly deferred to Write-Safety Guardrail (the operating layer), keeping the destructive-write confirmation decision in one place rather than scattered per-command. This is cross-spec relevant (it is the first *destructive-but-unconfirmed* governance write, and sets the "faithful surface, defer confirmation to the guardrail" stance for future destructive writes) → record in DECISIONS.md.

## Cross-cutting Concerns

**No sibling-coordination concern** — the defining contrast with 057. 055/056/057/058 have all landed, so the `proposal` group, `proposalSeam`, `glassfrog.Proposal`/`Document[Proposal]`, and the singular `proposal` render path are all present and proven on `main`. 059 reuses them unchanged; there is no first-to-land-creates contract, no minimal-subset fallback, and no rebase-onto-a-sibling risk. The only shared-file touch is **one registration line** in `newProposalCommand` and a `Short`-string widening — additive, beside the five existing leaves, mirroring how `propose`/`respond` attached.

**Failure mapping (no new outcomes)**: every failure routes through the landed `reportFailure` → `refineClientError`/`classifyClientError` chain: not-authenticated → the shared fail-safe (`UsageError(2)` NoCredentials / `RuntimeError(1)` CredentialError); transport → `NetworkUnavailable(6)`; `401`/`403` → `PermissionError(4)` (the Premium `403` included — ADR-1); `429` → `RateLimited(5)`; `404`/`422`/other non-2xx → `APIError(3)` with the RFC 9457 detail surfaced. **No status is intercepted** — the inverse of discard. The command adds no interpretation and never prints the token.

**Non-idempotent retry (silent conformance to §133)**: `withdraw` builds the same `NewRetryExecutor` as the rest, but 017's `isSafeMethod` restricts auto-retry-on-`429` to `GET`/`HEAD`, so a `POST` `429` surfaces once and is never silently re-sent — the withdraw cannot double-fire (which matters, since re-firing a succeeded withdraw would be a `422`, not a no-op).

**Output**: success renders through the same buffer-then-write path as `proposal get`/`proposal propose` — `output.RenderSuccess` over the raw `{data: Proposal}` for a built-in machine format, `writeHuman` over the decoded `ProposalView` for human/`-o template` — so a render failure leaves stdout empty and maps to `RuntimeError(1)`. No stderr advisory (ADR-2 — single success outcome, deletion legible in the data).

**Testing**: the seam injection keeps `runProposalWithdraw` pure over a fake transport — mirroring `proposal_propose_test.go` and `proposal_advance_bdd_test.go`. Unit tests drive every branch offline — `200` success (asserting the decoded/raw proposal renders **back in `draft`** with the `response_summary` cleared and exit `0`), `422` transition-not-allowed failure (already `draft`, or `withdraw` not offered), `404` not-found failure (asserting it is **not** swallowed as success — the contrast to discard), the Premium `403` (asserting it routes through `PermissionError(4)` with no plan-gate message), `429` (asserting the `POST` is not auto-retried), transport failure, not-authenticated, and a bad `--output` (a fail-fast `UsageError(2)` with a transport tripwire confirming **no request**). A focused test pins that the `POST` carries **no body and no `Content-Type`**, targets `/proposals/{id}/withdraw`, and that the command issues **exactly one** request and **no prior `GET`**. A godog BDD suite mirrors the driving scenarios (the per-command `*_bdd_test.go` convention; suite `Paths` names only its own feature file — LEARNINGS).

## Implementation Strategy

**Single phase — the `proposal withdraw` command**, a pure consumer of landed machinery and a structural twin of `proposal propose`. Build `newProposalWithdrawCommand` + `runProposalWithdraw` in `internal/cli/proposal_withdraw.go` by mirroring `proposal_propose.go` (resolve `--output` → assemble → one bodyless `POST /proposals/{id}/withdraw` with `out == &Document[Proposal]` → on success render the decoded/raw proposal; on any error `reportFailure` with no status interception); attach the leaf in `newProposalCommand` and widen the group `Short`; reuse the landed `proposalSeam`, `resolveRenderTarget`, `writeHuman`, `output.RenderSuccess`, the singular `proposal` render path, `reportFailure`/`refineClientError`/`classifyClientError`, and `NewRetryExecutor`; add BDD + unit tests. There is **no transport phase**, **no `internal/glassfrog` phase**, and **no `internal/render` phase** — the model and singular render are landed. The whole feature is PR-sized.

**Dependency**: this phase requires the `proposal` group, the `Proposal` model, the singular `proposal` render path, and (as a template) the `propose` leaf — **all landed on `main`** (055/056/057/058 merged). Unlike 057, there is no upstream sibling to wait on; 059 can be built directly off `main`.

## Risks

- **Copying discard's `404`-as-success divert from the wrong template (low likelihood, medium impact)**: discard (045 §337) folds its `404` into success, and an implementer could reach for it. *Impact*: a re-withdrawn or unknown proposal would wrongly report success. *Mitigation*: ADR-1 is explicit that withdraw intercepts **no** status (mirroring the landed `propose` leaf, not discard) — every non-2xx routes through `reportFailure` unchanged; a unit test pins that a `404` and a `422` both exit non-zero and surface the status. The correct template (`proposal_propose.go`) already does exactly this — copy it, not `tension.go`'s discard path.
- **Adding a destructive-write confirmation guard (low likelihood, low–medium impact)**: the deletion of responses tempts a `--force`/`--yes` flag or prompt. *Impact*: breaks the non-interactive contract and forks the uniform write surface. *Mitigation*: ADR-2 — no confirmation, no `--force`; the destructive-write guardrail is the separate Write-Safety Guardrail capability. A test asserts the leaf declares no flags (a stray `--force` is a cobra unknown-flag usage error).
- **Pre-read creep (low likelihood, low impact)**: `available_transitions` is available from the reads (056), tempting a client-side "is `withdraw` allowed?" check before the POST. *Impact*: an extra round-trip, a stale-snapshot race, a forked authority. *Mitigation*: ADR-1 / spec non-behavior — issue the POST and let the server's `422` enforce; a validation tripwire asserts exactly one request and no prior `GET`.
- **Premium `403` over-handling (low likelihood, low impact)**: the Premium gate makes a bespoke "not available on your plan" message tempting. *Impact*: forking the plan-gate signal that belongs to Plan-Limit Signalling. *Mitigation*: ADR-1 — the `403` stays a generic `PermissionError(4)`; a test asserts no plan-specific branch.

## What This Plan Does Not Cover

- **Protocol-level contract** — the exact flag/help/`Long` text for the `withdraw` leaf, the request-descriptor field shape, and the rendered-field selection are the **interface** skill's concern; the singular `proposal` render contract is 055/056's, reused. The names used here (`proposal withdraw <prp-id>`) are the spec-confirmed surface; treat them as the working contract, pinned at the interface stage.
- **Executable scenarios** — Gherkin for the driving scenarios is the **scenarios** skill's concern; the Driving Scenarios in spec.md are the source.
- **Task decomposition** — PR-sized units within the single phase are the **tasks** skill's concern.
- **The `Proposal` model, `Document[Proposal]` decode, the `proposal` group, the singular `proposal` render path, and the `propose` leaf template** — landed by 055/056/057; 059 reuses them.
- **Write-Safety Guardrail** — the operator-layer confirmation for destructive writes (deferred from ADR-2) is its own capability in the Agent operating surface. Out of scope.
- **Plan-Limit Signalling** — distinguishing the Premium-gate `403` from a permission `403` is its own capability; here the `403` routes through the shared classifier (ADR-1). Out of scope.
- **Re-editing or re-proposing after withdraw** — `withdraw` returns the proposal to `draft`; editing the draft and re-circulating it (Proposal Creation's edit surface, Advance to Circulation) are separate acts (spec non-behavior). This plan withdraws only.
- **Optimistic concurrency (`If-Match`)** — `withdraw` is a transition with no `If-Match` parameter; Guarded Writes (053) applies to field edits, and its `Request.IfMatch` field stays unused here. Out of scope per the spec non-behavior.
