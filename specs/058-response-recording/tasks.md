The render key (`proposal-response`) is unique to 058.
>
> **All cross-spec seams are landed on main.** 007/009/010/011/015/017/018/020/035 are Complete with their packages shipped — the generic `Document[T]`, `RetryExecutor`, `classifyClientError`/`Diagnose`/`Outcome`/`ExitCode` (011/015/031), the persistent `--base-url`/`--output`/`-o`, the 035-widened render flow, and — load-bearing here — the write-body `Request.ContentType` (042) and the opt-in `Request.IfMatch` (053). 058 reuses `ContentType="application/json"` and **leaves `IfMatch` empty** (append-create, not a guarded edit; plan ADR-3). It adds **no** new `Outcome`/`ExitCode`/generic/root flag. **`validateProposalResponse` lives with the proposal command code (beside the `validateProposalStatus`/`validateMeetingType` precedent), NOT in the shared `status.go`.**
>
> **The consume/respond write — the consent-window half of the Governance Proposals flow.** `proposal respond <prp-id> --response <no_objection|bring_to_meeting>` posts one member's response to a circulating proposal and surfaces the recorded `ProposalVote` (incl. the parent `proposal_status`, which reads `accepted` when this response triggered auto-acceptance). It is **Premium-gated** — a `403` (async proposals not enabled) classifies as `PermissionError(4)` through the shared chain with **no** plan-limit special-casing (Plan-Limit Signal is out of scope). A second response by the same person is the server's `422` (`APIError(3)`), never retried and never folded into success.

- [ ] **T001** [Shared] [P] Add the `glassfrog.ProposalVote` response model + the `{response:{value}}` request input — decode + marshal unit tests; `internal/glassfrog/proposal.go` — ~5 unit tests (full decode, nullable `proposal_id`→empty, `accepted` proposal_status, `Document[ProposalVote]`, request-body marshal shape)

## Phase 3: `validateProposalResponse` + response set [US4]

- [ ] **T003** [US4] [P] Add `validateProposalResponse` + the response set in the proposal command file — unit tests; a NEW required-value validator distinct from `validateProposalStatus`/`validateMeetingType` — in proposal command file, ~3 unit tests
  - **Scope**: In the proposal command file (`internal/cli/proposal.go` — **proposal-domain validators live with the proposal code, NOT the shared `status.go`**, per the 042/056 precedent), add a pure `validateProposalResponse(s string) error` mirroring the landed `validateMeetingType`/`validateProposalStatus` shape, over a **new** response set (`no_objection`, `bring_to_meeting`) in a single-sourced `supportedProposalResponses` map + a sorted `supportedProposalResponseNames()` helper. Unlike the optional `--status`/`--meeting-type` validators, `--response` is **required**: an **empty/omitted** value returns an error naming `--response` as required and listing the supported set; an unsupported non-empty value returns an error naming the value and the supported set. **Do not reuse `validateStatus`/`validateTensionStatus`/`validateProposalStatus`** — their vocabularies are wrong here (plan ADR-1). Pure, no I/O. (If cobra-level required-flag enforcement is also used, the validator still owns the closed-enum check and the supported-set message.)
  - **Acceptance criteria**:
    - `validateProposalResponse` returns nil for `no_objection` and `bring_to_meeting`
    - `validateProposalResponse("")` returns the required-error naming `--response` and listing the supported set (sorted) — empty does **not** pass (contrast the optional filters)
    - `validateProposalResponse("abstain")` returns an error naming the unsupported value and listing the supported set (sorted)
    - The set is single-sourced (one map/var); adding a value is a one-line change tracking the vendored spec enum
    - The shared `status.go` and the other validators are untouched; `go build`/`go vet` clean; unit tests pin supported + empty-required + unsupported cases
  - **Dependencies**: None — a pure new validator in the proposal command code. Startable immediately against current main.
  - **Plan reference**: Phase 3 (Validator); ADR-1 (required `--response` validated locally via a new validator)
  - **Interface references**: interface-cli.md — `--response` flag (required, validated set), Consistency Notes (one local validator, a new required set)
  - **Scenario references**: response-recording.feature: "A missing response value is rejected as a usage error", "An unsupported response value is rejected as a usage error", "An unsupported response value sends no request"
  - **Risk**: ⚠️ A new set, NOT a reuse of the status/meeting-type validators — reusing any accepts wrong values. ⚠️ `--response` is **required** — empty must fail (not a "no filter" no-op like the optional validators). ⚠️ Keep the set single-sourced. ⚠️ Place it with the proposal code, NOT in the shared `status.go`.
